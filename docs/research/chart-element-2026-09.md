# The chart element: state-of-the-art survey and decisions

Research date: 2026-09-03. Method: four researchers each took one facet
(chart web-component APIs and platform wiring; accessibility and colour;
timeline, cursor-sync and scrubber UX; rendering technology and the Rust
toolchain), searched and read primary sources, and wrote a facet report
(kept under docs/research/chart-element/). A fifth agent reconciled the
four, re-fetched the load-bearing claims itself, and wrote this note. The
verification ledger below records what was VERIFIED, CORRECTED or left
UNVERIFIED; statuses were sighted on the research date and must be
re-verified when a phase ships. Design tokens, the interaction machine,
opt-film and opt-machine referred to here are the site's own elements.


Synthesis and critique of the four facet reports for `<opt-chart>` and the series tokens on www.openpower.tools: R1 web components (`1-web-components.md`, final at 15:01, 250 lines), R2 accessibility and colour (`2-accessibility-colour.md`, final at 15:07, 272 lines), R3 timeline UX (`3-timeline-ux.md`, final at 14:49, 198 lines), R4 rendering and Rust (`4-rendering-rust.md`, final at 14:51, 155 lines). All four final versions were read in full for this revision, and the R3 and R4 versions on disk were confirmed by hash to be the ones used. The researchers fetched their sources on 2026-09-03; every re-fetch I made is also dated 2026-09-03 and is marked in the ledger and the source list. R2's computed palette figures come from its scripts in `docs/research/chart-element/palette` (refit.py to refit4.py); I re-ran refit3.py and refit4.py with `uv run --with colour-science --with numpy` on 2026-09-03 and reproduced every figure quoted below.

Constraints taken as given: Rust compiled to wasm, custom elements in Rust with shadow DOM, ElementInternals custom states and `::part`, no vendored JS, Trunk build, static GitHub Pages, ppc64le browser parity (Firefox on POWER has no wasm JIT), a site wasm of about 240 KB, design tokens on `:root` with Rust contrast tests (4.5:1 text, 3:1 non-text) in both themes. The 2026-09-01 decision for build-time classed SVG over vendored JS chart libraries is settled and not reopened here.

Repository facts I checked while synthesising, because several decisions depend on them. `crates/op-site/src/components/film.rs:19-24` (module doc) names the custom states `playing`, `pending` and `peeking`, the per-render `opt-film-time` broadcast, the `role=slider` chart and a polite live region. `film.rs:187` puts `role="slider"` with `aria-valuetext` on the whole chart `<svg>`. `film.rs:405-413` dispatches `opt-film-time` as a composed, bubbling CustomEvent whose `detail` is a bare f64 of seconds. `film.rs:415-433` moves the playhead by rewriting `x1`, `x2`, `cx`, `x` and `width` on four nodes each render, sets `value` on a `dom.slider` control (`film.rs:417-420`, which behaves like a native range input; its element type was not checked), then writes `aria-valuenow` and an `aria-valuetext` of the form "t seconds, frame k of n, chapter". `film.rs:576-602` implements the pending seek (`set_pending`, `commit`, `cancel`) with the `pending` state and live-region messages. `film.rs:1028-1096` handles Space and K (toggle), period and comma (one frame), ArrowRight and ArrowLeft (five frames), L and J (ten frames), Home and End, Escape (cancel), greater-than and less-than (speed) and digits (seek to tenths); there is no Page Up, Page Down or Shift plus arrow. `machine_diagram.rs:365-384` resolves `for=` with `getElementById` in `connected()`, returns silently when the target is absent, and reads `detail().as_f64()`. `crates/op-webc/src/lib.rs:145-147` is the element shim, whose constructor calls only `this.attachInternals()` and never `attachShadow`; `lib.rs:271-297` reads those internals through `Reflect` because the pinned web-sys has no ElementInternals binding. `film.rs:624` already uses `shadow_root()`.

## Agreements

1. Classed SVG with no colour literals, classes mapped to tokens by the shadow stylesheet. R1 findings 2 and 3 and recommendation 3, R2 recommendation 1, R4 recommendation 1. R1 names Highcharts styled mode as the production precedent and now lists its taxonomy in full (`.highcharts-series-{n}`, `.highcharts-graph` replacing the colour, line width and dash options, `.highcharts-plot-line` and `.highcharts-plot-line-label` for what we call marks). I re-fetched the Highcharts page: "no presentational attributes (like fill, stroke, font styles etc.) are applied to the chart SVG. Instead, the design is applied purely by CSS", and the stated limit that "layout and positioning of elements like the title or legend cannot be controlled by CSS". Geometry is the renderer's job; colour, dash and weight are the stylesheet's. R4 finding 1 adds poloto's class scheme as the one Rust precedent, unmaintained since 2023.

2. Data flows down through a property or a JSON data block; intents flow up as composed, bubbling events fired only from user gestures; high-frequency values are never reflected to attributes. R1 finding 14 and R3 finding 9 both quote web.dev's checklist ("Dispatch events in response to internal component activity", "Do not dispatch events in response to the host setting a property (downward data flow)", "You shouldn't reflect high frequency properties, e.g. currentTime in a video player"). R1's expansion adds the `_upgradeProperty` pattern for properties set before upgrade and the rule not to self-apply classes. R1 finding 7 adds TanStack Charts, whose element takes everything through an `options` property "not HTML attributes" (verified). R1 finding 15 adds the `<script type="application/json">` data block, inert to the parser and CSP-safe, and the by-reference variant in which several elements read one block by id.

3. One clock, one direction. R3's first recommendation states it: opt-film owns time and broadcasts `opt-film-time` on every render; a chart with `for=` renders the received time and never moves its own playhead in response to its own seek event. R1 recommendation 4 and finding 12 (the VLLNT scrubber's "The host owns the value and drives the playback loop; the component is pure presentation", svelte-p5's media sync that locks the timeline to media time and writes back through `seek`), and R4 recommendation 3 assume the same model; `machine_diagram.rs:365-384` already implements it for `<opt-machine>`.

4. Declarative Shadow DOM pre-render, hydrated through the existing root. R1 finding 20 and recommendation 2, R4 finding 18 and recommendation 6. Both warn that `attachShadow()` on a declarative root returns it emptied, so the element must check `internals.shadowRoot` (or `shadow_root()`) first. I verified the support versions (Chrome and Edge 111, Safari 16.4, Firefox 123) and the emptying behaviour. R1 adds that the design deliberately does not let several elements share one template, and R4 that the parser attaches the root as soon as the opening `<template>` is seen, so each pre-rendered chart paints as its bytes arrive.

5. Per tick, move a playhead group and rewrite one label; never rebuild series paths; coalesce clock events into one requestAnimationFrame. R4 recommendation 3 gives the mechanism, R3 priority 3 the motion policy (playhead updates stay; flights and ghost travel go under reduced motion; uPlot's "no transitions or animations" inside the SVG), R1 recommendation 5 restricts full re-render to resize.

6. Forced-colours mode keeps SVG author colours, so the element needs an explicit system-colour rule and series need non-colour cues. R2 finding 15 and recommendation 10, R4 findings 14 and 15 and recommendation 4 read the CSS Color Adjust spec identically, and I confirmed the reading (ledger row 11). R2's expansion quotes the spec's own note that the UA rule exists because "forced colors mode can't generally be usefully applied to illustrations", and both reports conclude that different roles (grid, series, band, playhead) need different system colours rather than one `currentColor`.

7. Strokes of 2 px at 3:1 against the surface, a dash pattern per series, direct end labels rather than a legend. R2 recommendations 3 and 4, R3 priority 3 (the film already draws direct series labels at `film.rs:250-259`), R4 recommendation 4 and finding 17. Okabe and Ito's page carries the same advice (thicken lines, vary line types, label on the graph), and R2's expansion adds their warning that for thin lines "use darker blue and orange" and avoid red on black.

8. Reduced motion keeps playhead position updates and drops easing and flights. R2 finding 7 and recommendation 9, R3 priority 3, R4 recommendation 3, all on SC 2.3.3's essential-motion exemption; R2 adds that motion the page starts by itself (a playing film) is SC 2.2.2, which the film's pause covers.

9. Verification through Rust-side tests plus CDP emulation of media features and vision deficiencies, with computed-style and accessibility-tree assertions. R2 recommendation 13 (now with `CSS.getComputedStyleForNode` and `Accessibility.getFullAXTree` from the protocol definitions) and R4 recommendation 8; the union is decision 27.

10. A shared skip list: scroll-driven animations, style queries, `interestfor`, the Context protocol and a shared `<opt-clock>` controller (R1 recommendation 10 and findings 16 to 18); Vello, plotters, charming and charts-rs (R4 recommendation 7); Plot-style click-to-stick (R3's expanded priority 1 recommends dropping it).

11. Every `<defs>` reference stays inside the chart's own shadow root, with ids prefixed per instance on light-DOM pages. R1 findings 22 and 23 and recommendation 2, R4 finding 12 and recommendation 1. R1's expansion confirms that two charts in their own shadow roots cannot collide, that only light-DOM SVG and cross-root `<use>` are at risk, and that the guarantee "rests on shipped engine behaviour and WebKit's layout tests rather than on spec text".

12. Nothing is announced during a peek or a pending seek; the slider's `aria-valuetext` carries the value; the total duration is not repeated on every change. R2 finding 17 and recommendation 11, R3 priority 2, both from the APG media seek slider, which R2's expansion confirms says "loses keyboard focus" in one place and "receives keyboard focus" in another (ledger row 25). The film's current valuetext repeats the total on every step (`film.rs:437-447`), which both reports want changed.

13. `vector-effect: non-scaling-stroke` on every stroke and a viewBox laid out in CSS pixels. R1 recommendation 5, R4 recommendation 2. They differ on how to keep text at CSS size without wasm; that is a conflict, resolved below.

14. The playhead and peek line must sit above the grid, enforced by the renderer's emission order (R3 finding 7's Kibana defect; R4 recommendation 1's group order).

15. A native range input is the cheapest universal fallback control. R1 finding 12 (the VLLNT scrubber is built on `input type=range` "so keyboard, pointer, and screen-reader support come for free"), R2 finding 4 (a native range passes SC 2.5.7 under the user-agent exception and the APG warns that touch assistive technologies may not drive custom sliders), and the film already updates a `dom.slider` control on every render (`film.rs:417-420`).

## Conflicts and resolutions

### Text measurement

Positions. R1 recommendation 7: measure tick and mark labels in the Rust build with rustybuzz plus ttf-parser against the served woff2, as boundsvg does, emitting `textLength` as the guard; R1 now names TanStack's "estimate at build, re-measure in wasm after `document.fonts.ready`" as its own fallback if the font pipeline is too much. R4 recommendation 5 and finding 22: build-time constant advance tables per font weight produced by ttf-parser as a build dependency, a runtime `measureText` on an OffscreenCanvas after `fonts.ready` only when `FontFaceSet.check` fails, `textLength` only where the estimate exceeds the slot ("it stretches short labels too, so it is a guard for overflow cases, not a default"), greedy label placement then remove-overlaps; R4 finding 8 adds that heavier shaping stacks "are unnecessary for Latin tick labels". R3's open question: is a ch-based width estimate plus a paint-order stroke acceptable, or should the wasm side measure once with `getComputedTextLength` and re-render?

Evidence. R4 finding 22: a per-glyph advance table makes measurement pure arithmetic (LogicAI: 2 to 4 million lookups per second against 200 to 400 thousand for `measureText`), ignores kerning pairs, covers Latin only; `measureText` silently measures the fallback font before `fonts.ready`; `getComputedTextLength` and `getBBox` force synchronous layout. R1 finding 25: every server-side charting stack either ships font metrics or degrades to estimates; a Deno badge generator found a canvas polyfill "off by a few pixels" and switched to glyph metrics from the font file, which is the advance-table approach; js-server-text-width packages per-glyph tables; boundsvg shapes with rustybuzz and accepts TTF, OTF or WOFF2 bytes. TanStack's SSR guide (verified): "The server uses deterministic fallback measurement unless you provide measureText. The browser host remeasures when fonts become available and schedules a new layout." R4 finding 19: web-sys 0.3.104 binds `FontFaceSet::{ready, check, load}`, `OffscreenCanvas` with `measure_text`, `TextMetrics::width` and `get_computed_text_length`, so every runtime path is available.

Resolution: advance tables, not shaping, with R4's runtime fallback. The chart's text is tick values, a time readout, units and short series names. Set in tabular figures, digits have identical advances and no kerning pairs, so a per-glyph advance table is exact for the strings that matter and within a pixel for the short words. Shaping buys correct kerning and ligatures for proportional prose, which the chart does not contain, at the cost of a shaping dependency in the build. A ch-based estimate is not acceptable for collision decisions (it is wrong by 20 to 40 percent for mixed digits and letters) but is acceptable as the last-resort fallback because `textLength` pins the rendered width to the slot. Measuring once with `getComputedTextLength` and re-rendering (R3's alternative) is rejected because it forces layout and only works after the wasm upgrade, which the no-wasm case never reaches. R1's point that the pre-rendered SVG "is the no-JS artefact and should be right on first paint" is accepted and is exactly why the build-time tables exist; they give first-paint exactness for the text we have. One practical detail neither report states: ttf-parser reads TrueType and OpenType, not woff2, so the build step needs the same face as a TTF or OTF file alongside the served woff2, checked for the same version (boundsvg's stack decodes woff2 if shaping is ever adopted). Our judgement, reconciling the reports by the actual content of the chart.

### Platform status and Reference Target

Positions. R1's summary still says "Reference Target (Chrome 152) forwards such references into a shadow tree" and its Baseline list says "Reference Target (Chrome 152 only)"; R1's expanded finding 18 is more careful: "Chrome Platform Status: origin trial 133 to 135, shipping 152; Mozilla's standards position is Positive (closed 2025-09-29); Gecko and WebKit both have prototype implementations; the WHATWG HTML pull request (#10995, opened 2025-02-05) was still being revised in July 2026 and a PR comment notes 'The pref in Gecko isn't enabled in Nightly'". R1 recommendation 6 proposes `popover="hint"` for the peek; R1 finding 18 records `interestfor` as Chrome 142 only, its event non-composed, and the attribute renamed from `interesttarget` during development.

Evidence. Chrome Platform Status API (updated 2026-07-22, re-fetched): implementation status "Origin trial"; Chrome desktop, Android and WebView milestone 152; origin trial 133 to 135; shipped milestone empty; Firefox "Positive"; Safari "No signal". The blink-dev Intent to Ship (re-fetched): estimated shipping 151; "Gecko and WebKit both have prototype implementations"; "there is no official commitment of support". Chromium Dash (re-fetched): milestone 152 reached stable on 2026-08-25. WebKit standards-positions issue 356: no position stated. MDN's popover attribute page (re-fetched): Baseline 2024 with parts varying, no per-value support for `hint`; R1 finding 18 adds Chrome's own `popover=hint` post (Chrome 133) and the Open UI explainer.

Resolution. R1's summary is corrected on tense: 152 was the planned milestone, the status entry still reads "Origin trial", and although Chrome 152 is stable I could not confirm the flag is on by default; R1's own finding 18 says as much. Firefox's position is positive, WebKit's is unstated with a prototype. All reports agree not to depend on Reference Target, and that stands: labels, descriptions, the slider and its readout live in one shadow tree (decision 15). When it becomes Baseline, the template can carry `shadowrootreferencetarget` naming the thumb so a page-level `<label for>` or `aria-controls` reaches it; nothing in the design blocks that. `popover="hint"` is not adopted (decision 19): its support could not be verified and the peek readout never needs the top layer. `interestfor` is not adopted, as R1 itself advised.

### Slider ownership and roles

Positions. R2 recommendation 5 and open question: role none or `graphics-document` on the svg, `role="slider"` on the thumb group, a host `role="group"`; and "If opt-chart is a separate element inside opt-film, the film should probably own the slider and the chart should expose only the graphics roles and the table". R1 recommendation 8 still says "Keep the chart a single tab stop with the existing role="slider"" while R1's own finding 24 records that `role="img"` on the root "collapses the element's subtree in the accessibility tree". R3 priority 1: the film owns time; the chart renders what it receives.

Evidence. R2 finding 17 quotes ARIA 1.2 directly: slider has "Children Presentational: True", and "The DOM descendants are presentational. User agents should not expose descendants of this element through the platform accessibility API." MDN's slider role page (re-fetched): "browsers automatically apply role presentation to all descendant elements of any slider element"; `aria-valuemin` defaults to 0 and `aria-valuemax` to 100 when omitted. The APG media seek slider (re-fetched): role none on the svg, the slider role "Set on the g element that represents as the movable thumb because it is the operable element that represents the slider value". The repository: `film.rs:187` puts `role="slider"` on the whole chart `<svg>`, and the film also updates a `dom.slider` control (`film.rs:417-420`).

Resolution. Ownership of state and ownership of a widget are different things, and there should be one slider per widget. The film owns the time value. A standalone chart, or a chart following a film as a sibling, exposes a slider on its own thumb group, computes `aria-valuenow` and `aria-valuetext` from the received clock, sets `aria-valuemin="0"` and `aria-valuemax` to the duration explicitly, and emits seek intents; it never sets time itself. A chart embedded inside the film's shadow tree (the film's own chart after phase 0) exposes only the graphics roles and the table, and the film's existing `dom.slider` control is the one slider, which R2's open question suggests and which also gives the film a native range for touch assistive technology and the 2.5.7 user-agent exception (agreement 15); the chart's thumb is then decoration. R1's "keep the existing role=slider" on the svg is rejected by R2's ARIA quote and by R1's own finding 24. The svg gets `role="graphics-document"` rather than the APG's `none` because the chart contains series content worth exposing (decision 15). `film.rs:187` is a defect in either arrangement and is fixed in phase 4. The one-slider-per-widget rule and the embedded-versus-sibling split are our judgement, following R2's suggestion.

### Cursor sync and the peek readout

Positions. R3 priority 1: cursor (peek line and playhead) always synchronised across chart, strip, stage and machine token; value readouts only on the view under the pointer; no floating tooltips on every synced view; "put the value at the cursor in the series' direct label or an axis readout"; priority 2: peek with pointerX semantics, snap to the nearest sample along x within about 40 px, carry the snapped time in the event. R1 recommendation 6: `<output part="peek" popover="hint">` anchored to the playhead with a transform fallback. R2 recommendation 11: nothing announced during peek or a pending drag. R3's dissent: Kibana's reporter wanted synced value popups, the charts team judged them noise; a per-series value in the direct label under the cursor "may satisfy both; this is untested".

Evidence. Grafana (re-fetched): Default, Shared crosshair, Shared tooltip as quoted in the ledger. Kibana (re-fetched): both sync settings exist; the defaults and the "high increase of noise" argument come from the pull request and issue R3 quotes. Observable Plot (re-fetched): pointerX divides the non-dominant distance by 100; the 40 px cutoff; click-to-stick; R3 quotes the `input` event sentence.

Resolution. Two cursors. The playhead is the committed time, owned by the film and synced to every follower by `opt-film-time`. The peek is uncommitted hover: the chart draws its own peek rule and readout and emits `opt-chart-peek` with the snapped time; the film uses that intent to preview the frame in the stage (its existing `peeking` state, `film.rs:451-500`), so the cursor is synced while no other follower draws a value readout, which is the Kibana "cursor on, tooltips off" level. R3's untested per-series-label variant is scheduled as an experiment in phase 3. The readout is an in-tree element inside the chart's box (an `<output>` in the shadow root positioned with a transform, or SVG text with a halo), not a popover: the top layer exists to escape overflow clipping and the readout never leaves the host box; `hint` support is unverified; anchor positioning is Baseline only since January 2026 and a transform does the job. Snapping follows Plot. The peek is silent for assistive technology.

### Event detail shape

Positions. R3's expanded priority 1: "Keep the detail an object with a time field rather than a bare number so it can grow (source, index of nearest sample) without breaking listeners; the existing opt-film-time bare-number detail should migrate the same way when opt-chart lands, or opt-chart should accept both"; R3's open question asks whether `opt-film-time` should become `{time, duration, playing}` and whether that breaks opt-machine. The repository: `opt-film-time` carries a bare f64 (`film.rs:405-413`) and opt-machine reads `detail().as_f64()` (`machine_diagram.rs:377`).

Resolution. The chart's intents carry objects from the start. `opt-film-time` migrates to `{ time, duration, playing }` in phase 2, in the same change that updates opt-machine to read the `time` field, with the chart accepting both shapes during the transition; both consumers are in this repository, so the migration is one commit and a snapshot test. The chart still needs `duration` in its own spec for the no-wasm pre-render; the event's `duration` is a cross-check. `playing` in the event lets the chart mirror the film's state without polling `film.matches(':state(playing)')`. Established practice (web.dev via R1 and R3), applied as our engineering choice.

### Gridlines and non-text contrast

Positions. R2 finding 1 and recommendation 3: 1.4.11 makes value gridlines graphical objects, yet "grid and ticks 1 px are acceptable on the explicit basis that tick labels, the peek readout and the table carry the values (record that reasoning in the test and the docs). Do not raise the grid to 3:1; keep it muted and treat it as ancillary, which is what both the WCAG example and the APCA author allow when values are readable elsewhere." R4 recommendation 4: thicker strokes and a solid grid under `prefers-contrast: more`; under forced colours, gridlines `CanvasText` at reduced opacity. R1 recommendation 3 maps the grid to the existing `--op-border` token and tick labels to `--op-muted`.

Evidence (re-fetched, and quoted at greater length by R2's expansion): "To perceive the values of each line along the chart you need to discern the grey lines marking the graduated 100 value increments"; "The graphical objects are the lines in the graph, including the background lines for the values"; the exception when "The information is available in another form, such as in a table that follows the graph" or "text embedded or overlaid conveys the same information, such as labels and values on a chart"; "2.999:1 would not meet the 3:1 threshold"; the anti-aliasing caveat and its advice to "avoid particularly thin lines and shapes, or to use a combination of colors that exceeds the normative requirements"; conformance is evaluated on the specified colours, not the anti-aliased pixels. SAPC-APCA discussion 117 (re-fetched): gridlines are "ancillary".

Resolution. There is no real conflict: R2 speaks of the default rendering, R4 of the high-contrast preference. Default: the grid is muted and 1 px, permitted only by the alternative clause because tick labels, the readout and the data table present every value; the palette test records that reliance in its name and failure message so that removing the table or the tick labels fails the test for the right reason. Under `prefers-contrast: more`: the grid becomes solid at 3:1 and series strokes go to 2.5 px (R4), because the user has asked for more. Under forced colours: the grid is `GrayText` (R2's expanded recommendation 10), a real system colour designed to be subordinate, with R4's opacity trick as the fallback if `GrayText` proves invisible on some palette. Series strokes are never muted: 2 px at 3:1 on all three surfaces is the floor, the test does not round, and APCA Lc is reported alongside because the thin-line caveat is exactly what WCAG 2's ratio does not model. Token naming follows R1 where possible: `--op-grid` defaults to the existing `--op-border` value and tick labels use `--op-muted`, so the existing contrast tests already cover them; the band, playhead and peek get new tokens because 1.4.11 governs them and nothing existing fits (R2).

### Forced-colours palette

Positions. R2's expanded recommendation 10: series strokes `CanvasText` with dashes and end labels carrying identity, the highlighted or hovered series `LinkText`, playhead and focus ring `Highlight`, band transparent with a 1 px `CanvasText` stroke, grid `GrayText`, labels `CanvasText`; `forced-color-adjust: auto` on the svg "so currentColor updates"; re-run the contrast tests against the emulated light and dark forced palettes. R4 recommendation 4: text, axes and series `CanvasText`, band and played bar `Highlight` with `HighlightText`, background `Canvas`, gridlines `CanvasText` at reduced opacity; R4's open question asks whether chapter bars should use `Mark`. R4 recommendation 6 rules out `<foreignObject>` labels because `svg|foreignObject { forced-color-adjust: auto }` would force their colours separately.

Evidence (re-fetched). CSS Color Adjust CR 7 May 2026: `fill` and `stroke` are in the force-adjusted list; the UA rules `svg|svg { forced-color-adjust: preserve-parent-color; } svg|foreignObject { forced-color-adjust: auto; }`; `preserve-parent-color` keeps author colours and passes only an inherited `color` through; "if its computed value is a color other than a system color, its used value is instead forced to a system color", so author-specified system colours survive. R2 finding 14 adds (researcher-sighted) that the same CR standardises forced-colours emulation for automation with a theme of none, light or dark and defined system-colour mappings. The APG seek slider (re-fetched): the ring uses `currentcolor` and "The SVG element needs to have the CSS forced-color-adjust property set to auto for the currentcolor value to be updated in high contrast mode". R4 finding 16 lists the current keywords including `Mark`, `MarkText`, `LinkText`, `GrayText` (researcher-sighted).

Resolution. Series, axes, ticks, marks and chapter ticks `CanvasText`, dashes carrying identity; the hovered or focused series `LinkText` (R2), which is guaranteed distinct from `CanvasText`; grid `GrayText` (R2); band with no fill, a dashed `CanvasText` outline and a `CanvasText` label (R2), with `Mark` and `MarkText` as the pair to try if a filled band is ever needed (R4's question); the played region of the track `Highlight` with `HighlightText` (R4); the playhead a cased line, `Highlight` core with a 1 px `CanvasText` outline, visible against `Canvas` on any palette and distinct from the series; the peek rule `CanvasText` dashed; the focus ring `Highlight` (R2 and R4 agree); background `Canvas`; no `<foreignObject>`. `forced-color-adjust: auto` on the svg is adopted, reversing my earlier reading: every paint inside the chart is a system colour under the forced-colours block, and the spec says author system colours are kept, so letting the UA force is a no-op for our paints while it guarantees that the ring's `currentColor` updates in engines that do not default the svg to `preserve-parent-color` (R2's reading of the APG note). The test runs under both emulated forced palettes (decision 27). The cased playhead is our judgement; the rest follows R2 and R4 and the spec.

### Custom state names

Positions. R3 keeps `following`, `peeking`, `scrubbing` but says opt-chart "should use the same names where the meaning is the same" as the film's `playing`, `pending`, `peeking`, and recommends dropping the click-to-stick lock. R1 recommendation 4: mirror the film's `following`, `playing`, `pending`, `peeking`, and R1 finding 21 confirms `::part(playhead):state(peeking)` is valid selector chaining.

Resolution. The film's vocabulary: `pending` rather than `scrubbing` (same meaning), `peeking`, `playing` mirrored from the film's event, plus `following` once the clock is bound. No lock state. Custom states are Baseline since May 2024 (verified) and are set through the shim's internals.

### Keyboard step units and the Page keys

Positions. R2 recommendation 12: arrow keys 1 s, Shift plus arrow 10 s "(or the film's existing J/K/L semantics)", Page Up and Page Down previous and next chapter, Home and End, Space or K toggles play, Escape cancels; intercept keys only while the chart has focus (Chartability's "Controls override AT controls" heuristic) and never intercept Tab; R2 recommendation 5 wants a visible instructions line naming those keys. R3's expanded priority 2: the film's arrows step five frames and J and L ten (verified locally); add Shift plus arrow as the larger jump ("ten samples or one second, whichever we pick, but pick one and document it") and Page Up and Page Down as the ARIA larger step; consider Ctrl or Alt plus arrow for chapters as YouTube does. The APG slider pattern: Page keys optionally move "by an amount larger than the step change".

Resolution. Consistency between the two widgets wins over R2's seconds: the chart steps in its own samples (comma and period one, arrows five, J and L ten), matching the film's frame steps when samples are per frame, with a `step` attribute for sparser data; Shift plus arrow is one second (R3's "pick one"); Page Up and Page Down jump by chapter (R2), with Ctrl or Alt plus arrow as an alias for YouTube parity (R3); Home and End; Space and K emit the toggle intent; Escape cancels a pending seek; keys act only while the chart has focus and Tab is never intercepted (R2). The visible instructions line (decision 15) documents exactly these. Phase 0 adds Page keys and Shift plus arrow to the film so both widgets match. Our judgement over two reports that disagree on units and on the Page keys.

### Pre-render width and text size without wasm

Positions. R1's open question: one pre-rendered width plus wasm re-render, or two or three pre-rendered widths selected with container queries for the no-JS case? R1 finding 13: Build UI keeps text CSS-sized with three SVGs (axes without `viewBox`, a nested `viewBox="0 0 100 100" preserveAspectRatio="none"` plot) and swaps label lengths with container queries; R1 recommendation 5 notes that `container-type: inline-size` on the host "also lets the stylesheet hide the chapter bar or thin the ticks below a width". R4 recommendation 2: never rely on viewBox stretching; R4 finding 23: token-sized text is only guaranteed when the viewBox equals the rendered box.

Resolution. With wasm, one pre-render suffices because the ResizeObserver re-layout makes user units equal CSS px. Without wasm, which on this site is the whole experience on ppc64le Firefox and on any JS-disabled load, the pre-render scales with its viewBox and 12 px labels shrink with it. The chosen order: one pre-render at the content column's design width (640 px unless the site's measure differs), scaled by viewBox with `preserveAspectRatio` and non-scaling strokes; container queries in the shadow stylesheet, which need no JS, hide every second tick label and the chapter bar below a width so the scaled render stays uncluttered (R1); phase 2's JS-disabled check measures the effective label size at 360 px and at the narrowest content width the site allows, and only if labels fall under about 10 px effective does phase 2 add a second, narrow pre-render switched by a container query. Build UI's split-layer trick is not adopted because it doubles the renderer's output model and complicates hit-testing. Our judgement with an explicit measurement trigger.

### Palette lightness bands and the dark-theme floor

Positions. R2's original recommendation and my earlier draft: one lightness per theme at the Okabe-Ito hue angles, with a second lightness level only if the CVD floor failed. R2's expanded finding 13 and recommendation 1, from its refit scripts, which I reproduced: at one lightness the palette loses the lightness spacing Okabe-Ito depends on ("Sky blue and blue are chosen so that they are distinguishable with there difference in brightness and saturation"; computed hue angles sky blue 236 and blue 244 are 8 degrees apart, and vermilion 48, orange 77 and yellow 105 sit within 60 degrees); six hues at one L give a worst-case pairwise CIEDE2000 of 3.6 in normal vision (the two blues) and 0.7 to 3.0 under protanopia and deuteranopia (orange, yellow and vermilion merge); five hues in one band bottom out at 4.2 to 5.5 (orange versus vermilion); four hues (orange, bluish green, blue, reddish purple) in one band give 37.5 normal, 12.1 protan, 15.9 deutan, 7.9 tritan; six hues in two bands give 11.7, 10.9, 11.1, 8.5 on white (bands L 0.55 and 0.65, chroma cap 0.16) and 10.9, 9.4, 9.2, 8.5 on #2B415F (bands 0.66 and 0.76). R2 finding 10: on white, WCAG 3:1 already sits at about APCA Lc 56 to 60, so the two models agree; on the dark surface #2B415F, colours that just pass 3:1 reach only Lc 31 to 37, Lc 45 needs about 4.3:1 (bands 0.75 and 0.85, worst-case distances 10.7, 8.6, 8.1, 7.9) and Lc 60 needs about 5.8:1 (bands 0.83 and 0.92, distances down to 6.6, pastel colours). R2 also measured the brief's current colours: #0072B2 at 2.00:1 and #D55E00 at 2.68:1 on #2B415F, #E69F00 at 2.25:1 on white, so the present palette fails today. Datawrapper (R2 finding 13, researcher-sighted): a dark-mode palette needs different lightness per colour so it survives greyscale; a bright yellow "will turn into a brown".

Resolution. Two lightness bands per theme from the start, not one; a default of four series in one band (orange, bluish green, blue, reddish purple), which is the largest set that is robust in one band; six series only when needed, from R2's computed two-band set (orange, sky blue and reddish purple in the darker band; bluish green, yellow rendered as olive, and blue in the lighter band), which drops vermilion and black rather than yellow and black as my earlier draft did, because the search shows orange and vermilion are the pair that collapses under deuteranopia. Dark theme floor: APCA Lc 45 (bands about 0.75 and 0.85) rather than WCAG 3:1 alone, because 2 px strokes on a dark surface at 3:1 are precisely the thin-line case the WCAG text tells authors to exceed, Lc 45 keeps every CVD distance at or above 7.9, and the Lc 60 floor costs too much separability (6.6) and turns the palette pastel. Light theme: bands 0.55 and 0.65 with the 3:1 floor, since WCAG and APCA agree there. The Rust test regenerates these numbers from the tokens (decision 23); R2's figures are estimates from one model at severity 1.0 and the test carries a few units of slack for model differences (R2 finding 14). Our judgement, informed by R2's reproduced computations; the dark-theme floor is the one choice R2 explicitly left to the team.

### Announcing chapter changes during playback

Positions. R3's open question asks whether the live region should announce chapter changes during playback; my earlier draft said no. R2's expanded recommendation 11: the status region receives one short message on commit, on play and pause, "and when a chapter boundary is crossed while playing (rate-limited to chapters, never per sample)"; PhET's model separates the per-change object response (valuetext) from a context response after an interaction (R2 finding 19).

Resolution. Announce chapter entry while playing, as a few-word polite status message rate-limited to chapter boundaries (which YouTube requires to be at least 10 s apart). A blind listener following playback otherwise learns of a chapter change only from the debounced valuetext, and only while the thumb is focused; the status message is the context response PhET describes. Reversal of my earlier draft, adopting R2.

### Markers: always, or only without labels

Positions. R4 recommendation 4: "a dash pattern and a mark shape per series in all modes (WCAG 1.4.1)". R2 recommendation 4: a dash pattern per series and a direct end label, "marker symbols at sampled points if series are ever drawn without labels". R1 recommendation 3 lists no markers.

Resolution. Dashes always; markers at sparse samples only when a series has no end label (a legend fallback case) and in forced-colours and high-contrast modes, where colour is gone and the extra cue is worth the ink. 1.4.1 is satisfied by dash plus label; markers on every series at every sample would be the chartjunk Tufte and Eikenes warn about (R2 finding 9). Our judgement.

### Chapter ownership and where chapter titles appear

Positions and evidence as in the previous revision: R3 asks whether the chart derives chapters from the machine's marks as the film does, and places chapter ticks in the track with titles in the readout; R2 recommendation 6 adds previous and next chapter as real buttons in the film's control bar as the single-pointer alternative.

Resolution. op-pages derives both the film and the chart from the machine trace at build time; the chart's JSON carries the chapter boundaries it draws as ticks, the film keeps the titles it speaks; nothing is transferred at runtime. Chapter ticks in the chart are focusable buttons named by the chapter title (decision 20); the film gains previous and next chapter buttons (decision 19). Mark labels get greedy collision removal with the mark nearest the playhead winning (R3).

## Decisions

Each decision states what, why, which reports and sources support it, and whether it is established practice or our judgement. "Verified" refers to the ledger above.

### Data shape

1. Intake is a JSON data block plus a property. `<opt-chart for="film-id">` holds one `<script type="application/json">` child with `series` (id, label, unit, dash index, marker index), `rows` as `[t, v1, ..., vN]` with `null` for missing samples, `marks` (t, label), `band` (t0, t1, label), `chapters` (t, title), `duration` and an optional `y` domain; the same object is settable through a never-reflected `data` property, with web.dev's `_upgradeProperty` pattern so a `data` set before upgrade is not lost (R1 finding 14); attributes exist only for the primitives `for`, `initial-width`, `ratio` and `step`. The Rust serialiser escapes the sequence `</script` inside the block (R1 recommendation 1). A `data-block="id"` attribute that references a shared block by id (R1 finding 15's by-reference variant) is reserved for a later version so a film and a chart can share one dataset without duplication. Reasoning: rich data belongs in a property, not an attribute (web.dev via R1 and R3); a data block is inert and CSP-safe and exists in the static HTML before any wasm runs, which the pre-render needs; TanStack takes everything through one options property (verified); the columns-of-rows shape keeps series aligned on one time axis and lets a path emitter draw gaps (R4 recommendation 1). Dissent: R3 asked about light-DOM tables as intake, and R1 mentions declarative `<opt-series>` children as a possible v2; neither is adopted now because the visible table is rendered from the JSON (decision 16) so authors write one thing. Established practice, with the field list our judgement.

2. Time is seconds as an f64 throughout, and event details are objects. The chart keeps only the last received time, the `duration` from its spec and, while a drag is pending, the pending time; it never advances time on its own. Its intents carry `{ time }` (later `{ time, source, index }`). `opt-film-time` migrates from a bare number to `{ time, duration, playing }` in phase 2, with opt-machine updated in the same change and the chart accepting both shapes during the transition (R3's expanded priority 1; the conflict on event detail shape). Established practice (web.dev via R1 and R3), applied as our engineering choice.

### Wiring

3. Binding to the clock. In `connected()`, resolve `for` first in the chart's own tree scope (`getRootNode().getElementById`, R1 recommendation 4's "in the chart's tree scope") and then in the document, exactly as `machine_diagram.rs:365-384` does for the document case, and subscribe to `opt-film-time` on that element; additionally register one listener for `opt-film-time` on the document that accepts events whose `target.id` equals `for`, so that a chart upgraded before its film is defined, or a film inserted later, still binds; set the `following` state once the first event arrives; expose a `forElement` property beside `for`, mirroring `commandForElement` and `interestForElement` (R1 finding 18), so scripted pages can wire across roots without ids. Reasoning: `opt-film-time` is composed and bubbling (verified), so a document-level listener sees it regardless of upgrade order, which answers R4's question about a declarative root that exists before the wasm upgrades; the tree-scope lookup lets a chart inside another element's shadow root find a film in the same root; attribute reflection through a common parent, Nightingale-style (R1 finding 17), would force nesting and is not adopted. Our judgement, built on R1 recommendation 4 and the existing opt-machine code.

4. Intents. `opt-chart-seek` with `detail: { time }` on a press without movement, on a key that moves the thumb, and on release of a pending drag; `opt-chart-peek` with `detail: { time }` on hover and during a pending drag and `detail: { time: null }` when the pointer leaves or the drag is cancelled; both composed and bubbling, dispatched only from user gestures, never because a property was set (web.dev via R1 finding 14). The film subscribes and applies them, so the chart's playhead moves only when the film's clock says so. There are no separate commit or cancel events (R1's open question): commit is the seek intent and cancel is the null peek. `opt-chart-toggle` on Space and K is added in phase 3 so keyboard users focused on the chart can play and pause; R3 did not list it and it is our judgement. `opt-chart-range` on Shift plus drag (R3 priority 3) is deferred until the interaction report needs it, as R3's dissent advises. Established practice.

5. Custom states. `following` (clock bound), `peeking` (hover or pending preview showing), `pending` (press-drag in progress) and `playing` (mirrored from the film's event), set through the shim's internals (`op-webc/src/lib.rs:271-297`) so pages can write `opt-chart:state(pending)` and `opt-chart::part(playhead):state(peeking)` (R1 finding 21 confirms the chaining). `CustomStateSet` is Baseline since May 2024 (verified). No lock state (the conflict on state names). Established practice, names our choice.

### Theming

6. Tokens, classes and parts. New tokens `--op-series-1` to `--op-series-6`, `--op-band`, `--op-playhead` and `--op-peek` on `:root` per theme, defined through whatever mechanism the existing tokens use (`light-dark()` is Baseline since May 2024 and needs `color-scheme: light dark`, verified, if that mechanism is wanted; R1 notes it is optional because the tokens already flip per theme). `--op-grid` defaults to the existing `--op-border` value and tick labels use `--op-muted` (R1 recommendation 3), so the site's existing contrast tests already cover them, with R2's requirement that the grid, band and playhead be tested too (decision 23). Classes emitted by the renderer, following R1 recommendation 3's list: `series-N`, `grid`, `axis`, `tick`, `tick-label`, `mark`, `mark-label`, `band`, `chapter`, `playhead`, `playhead-label`, `peek`, `plot`, `background`, `ring`, `readout`, plus a `data-series` attribute on each series group for hit-testing; the shadow stylesheet maps each class to its token (`.series-1 { stroke: var(--op-series-1) }`, `.grid { stroke: var(--op-grid) }`, `.tick-label { fill: var(--op-muted) }`); the same names are exported as parts so a page can write `opt-chart::part(series-2) { stroke-dasharray: 4 2 }`. R4's BEM names are not needed inside a shadow root, where classes are private and parts are the public surface. No `contrast-color()` for series or labels: it returns only white or black, browsers may use different algorithms, and mid-tones fail (verified); the Rust test is the source of truth (R1). Reasoning: Highcharts styled mode is the precedent for index-based series classes and Vaadin for the token tier (R1 findings 2 and 3, verified for Highcharts); custom properties inherit into the shadow tree without bridging (R4 finding 12, researcher-sighted); Lit's guidance that per-instance theming goes through custom properties (R1 finding 13). Established practice.

7. Forced colours. A `@media (forced-colors: active)` block in the shadow stylesheet, plus `forced-color-adjust: auto` on the svg: text, axes, ticks, series, marks and chapter ticks `CanvasText`, the dash table carrying series identity; the hovered or focused series `LinkText`; the grid `GrayText`; the band with no fill, a dashed 1 px `CanvasText` outline and a `CanvasText` label, with `Mark` and `MarkText` as the pair to try if a filled band is ever needed; the played region of the track `Highlight` with `HighlightText`; the playhead a cased line (`Highlight` core, 1 px `CanvasText` outline); the peek rule `CanvasText` dashed; the focus ring `Highlight`; background `Canvas`; no `<foreignObject>` anywhere. Reasoning: the UA stylesheet's `preserve-parent-color` keeps author SVG colours, so without this block six coloured series would stay six colours on a forced palette (spec, MDN and Edge blog verified); author system colours survive forcing, so `forced-color-adjust: auto` is a no-op for our paints and makes the ring's `currentColor` robust (the APG note, verified; R2 recommendation 10); `Canvas`/`CanvasText` and `Highlight`/`HighlightText` are the guaranteed pairs, which is why the band is outlined and the playhead cased. Sources: R2 finding 15 and recommendation 10, R4 findings 14 to 16 and recommendations 4 and 6, CSS Color Adjust CR 2026-05-07. The cased playhead is our judgement.

8. High contrast preference. Under `prefers-contrast: more`, the grid becomes solid at 3:1 against the surface and series strokes rise to 2.5 px (R4 recommendation 4 and finding 16). Our judgement on the exact numbers.

9. Print. `print-color-adjust: exact` on the band and the playhead, peek and readout hidden in `@media print` (R4 recommendation 4 and finding 16; the Baseline claim for `print-color-adjust` not re-fetched; low stakes).

### Sizing and pre-rendering

10. Declarative pre-render and hydration. op-pages emits `<opt-chart for="..." data-hash="...">` containing `<template shadowrootmode="open" shadowrootdelegatesfocus>` with the classed SVG, the shared stylesheet, the caption, summary and instructions line, the readout, the focus ring, the table and the status region, rendered at `initial-width` (640 by default, TanStack's value, verified), plus the JSON data block as a light-DOM child. On upgrade the element reads `shadow_root()` (already used at `film.rs:624`); if a root exists and `data-hash` matches the hash of the data block, it caches handles and hydrates; otherwise it renders and attaches. It never calls `attach_shadow` on an existing root, because that empties it (web.dev, verified); the op-webc shim attaches only internals (`lib.rs:145-147`, checked), so nothing else can. The site stylesheet carries `:not(:defined) > template[shadowrootmode] { display: block }` (web.dev via R4 finding 18) so browsers without Declarative Shadow DOM still show the chart's content as plain markup. Reasoning: on ppc64le Firefox and on any JS-disabled load the pre-render is the whole experience, so it must include everything a reader needs; parser-attached roots paint as their bytes arrive (R1 finding 20, R4 finding 18). Sources: R1 recommendation 2, R4 recommendation 6, DSD support verified. Established practice.

11. Host box and resize. `:host { display: block; container-type: inline-size; aspect-ratio: var(--op-chart-ratio, 16 / 6) }` plus `:host([hidden]) { display: none }` (web.dev via R1 finding 14); a ResizeObserver triggers a full re-layout at the measured width inside one requestAnimationFrame; the viewBox equals the box in CSS px so user units are CSS pixels and text stays token-sized; `vector-effect: non-scaling-stroke` on every stroke; `shape-rendering: crispEdges` only on axis-aligned grid lines (R4); container queries in the shadow stylesheet hide every second tick label and the chapter bar below a width so the no-wasm scaled render stays uncluttered (R1 recommendation 5). One pre-render only, with the measurement trigger for a narrow variant described in the conflict on pre-render width. Sources: R1 recommendation 5 and finding 13, R4 recommendation 2 and finding 23. Established practice, with the single-width choice our judgement.

### Renderer

12. A pure Rust renderer crate with no runtime dependencies. Input: the spec and a box (width, height in CSS px, margins from the tokens' known values). Output: the SVG string and a `Layout` struct holding the plot rectangle, the time scale (t to x and back), the y scales and the placed label boxes; the element keeps the `Layout` for hit-testing so seek and peek need no DOM measurement (R4 suggested host attributes; the struct avoids a DOM round trip and the layout is deterministic from the spec). Emission rules: one `<path>` per series with `M` and `L` commands at one decimal and gaps for missing samples; groups emitted in the order `grid`, `axes`, `series`, `marks`, `band`, `chapters`, `peek`, `playhead`, `labels`, which is the z-order R3 asks the renderer to enforce; no colour literals; ids only for one `<clipPath>` per instance, prefixed with the host id or a per-instance counter (R1 finding 23, R4 finding 12); `part` on the svg, the playhead and each series; a single `String` builder with fixed-precision formatting (R4 recommendation 7). Ticks by a port of d3-ticks (about 60 lines); axis-labels' Extended algorithm evaluated later only if it costs under about 2 KB of wasm. Per-column min and max decimation, not LTTB (R4 finding 11), only when a series has more points than the plot is wide, which film data (tens to hundreds of samples) will not trigger; a guard with a boundary test. Reasoning: the ApexCharts benchmark (verified, vendor-run) shows a single path is cheap at any realistic count and that cost comes from node count and per-frame churn; poloto is unmaintained (verified); R4's 20 KB wasm budget measured with twiggy is adopted as a phase gate. Sources: R4 recommendations 1 and 7, findings 1 to 3 and 9 to 12. Established practice for the SVG shape; the `Layout` contract is our design.

13. Per-tick update. On each `opt-film-time`, store the time and, if no frame is pending, call `request_animation_frame` once; in the frame: compute x from the cached scale; if the move is under half a pixel and the label is unchanged, return; else set `transform="translate(x 0)"` on the playhead `<g>`, set the readout's text, set the played rect's `width`, update `aria-valuenow` and (debounced, decision 18) `aria-valuetext`; skip frames while `document.hidden`; never touch series paths, marks, grid or axes. Easing only as a CSS transition on the playhead transform, driven by the site's motion tokens; never animate `x1`, `x2`, `cx` or `d`, which repaint (R4 finding 20, researcher-sighted). The film's own chart writes four nodes' geometry each render (`film.rs:415-433`); moving it to a group transform is scheduled in phase 0. Sources: R4 recommendation 3 and finding 21, R3 priority 3. Established practice.

14. Text metrics and label placement. At build time, a build dependency on ttf-parser reads the served face (a TTF or OTF copy of the same version kept beside the woff2) and emits constant advance tables per weight used, Latin plus the punctuation the chart uses; the renderer measures with those tables; tick and readout text use tabular figures so the measurement is exact; `textLength` is emitted only where a label must fit a fixed slot; at runtime, if `FontFaceSet.check` reports the face missing, the element waits for `fonts.ready`, measures with `measureText` on an OffscreenCanvas (bindable in web-sys 0.3.104, R4 finding 19) and re-lays out once (the TanStack pattern, verified; R1's own fallback). End labels and mark labels are placed greedily (candidate positions around each anchor, lowest overlap first, inside the plot) then overlapping survivors are removed, deterministically; axis tick labels are thinned left to right with a minimum gap (R4 finding 24, R3 finding 14); a `paint-order: stroke` halo in the surface colour keeps labels legible over lines and gridlines (Datawrapper via R3, Plot's crosshair). Sources: R4 recommendation 5 and findings 22 and 24, R1 findings 16 and 25, R3 finding 14, the text-measurement conflict. Established practice for the mechanisms; tables over shaping is our judgement.

### Accessibility

15. Structure (R2 recommendation 5, adopted with two additions). The host takes `role="group"` through internals, with `aria-labelledby` pointing at a visible title in the shadow tree and `aria-describedby` at a one-paragraph summary (series names, unit, range, number of chapters, the takeaway) and a short instructions line naming the keys, because Chartability rates missing instructions and missing summaries as critical (R2 finding 18) and Highcharts advises visible over hidden descriptions. The `<svg>` takes `role="graphics-document"` and `aria-labelledby` the title. A `<g aria-hidden="true">` holds grid, ticks, band and decorative marks. Each series `<g role="graphics-object">` carries `aria-label="Name, N samples, min to max unit, from t0 to t1"` with its path and its end-label text `aria-hidden` so the name is not exposed twice. A `<g role="graphics-object" aria-label="Chapters">` holds one `<g role="button" tabindex="-1">` per chapter with the chapter name and time and a 24 by 24 px transparent hit rect; marks likewise. The thumb `<g role="slider" tabindex="0">` carries `aria-labelledby` the title, `aria-valuemin="0"`, `aria-valuemax` set to the duration, `aria-valuenow` and `aria-valuetext`, and contains the playhead line, its hit rect, the visible time readout (inside the slider group so it is not read twice, the fix from APG issue 3257) and the focus-ring rect. After the svg: an empty `<div role="status" aria-live="polite">` present from first render, and the table (decision 16). The svg is never `role="slider"` or `role="img"`; the host is never `role="slider"`. When the chart is embedded inside the film's shadow tree, the thumb group is decoration and the film's own `dom.slider` is the slider (the conflict on slider ownership). `film.rs:187` gets the same restructuring. Fallback: where a screen reader ignores the graphics roles, the series groups read as labelled groups. Sources: R2 recommendation 5 and findings 16 to 18, MDN slider role and the APG seek slider (verified), R1 finding 24. Established practice; the aria-hidden ticks and the embedded-case rule are our judgement.

16. A real table. The shadow root contains a `<table>` with `th scope` headings (time, chapter, one column per series with units) behind a `<details>` disclosure, pre-rendered so it exists without JS, with mark and chapter rows. Reasoning: 1.4.11's alternative clause (verified) is what permits the muted grid; Watson's ARIA-table-in-SVG worked only in some browser pairs and `aria-describedby` flattens structure (R2 finding 18, researcher-sighted); Chartability: "Providing both can satisfy conflicting accessibility needs for different audiences." Established practice.

17. Keyboard. One tab stop into the chart with `delegatesFocus` (declared as `shadowrootdelegatesfocus` on the template) landing on the thumb; roving `tabindex` between the thumb, marks and chapter ticks, moved with arrow keys while a mark or chapter is focused, never intercepting Tab; keys on the thumb: comma and period one sample, Left and Right five samples, J and L ten samples (matching the film's frame steps at `film.rs:1028-1096`; the `step` attribute overrides the sample step), Shift plus arrow one second, Page Up and Page Down by chapter with Ctrl or Alt plus arrow as an alias, Home and End, Escape cancels a pending seek, Space and K emit the toggle intent, digits seek to tenths; keys act only while the chart has focus (Chartability's "Controls override AT controls"); every key emits an intent in seconds and the chart moves only when the clock answers; a keyboard seek commits immediately and never enters the pending state (R2's open question). The instructions line documents exactly these. Phase 0 adds Page keys and Shift plus arrow to the film. Sources: R3 priority 2 and finding 13, R2 recommendations 5 and 12 and finding 17, R1 finding 24, the film's key table (verified locally), the conflict on step units. Established practice; the Page-key assignment and the sample units are our judgement.

18. Announcements. No live region for peek or pending. `aria-valuetext` reads "1 minute 32 seconds" with the chapter title appended; the duration ("of 4 minutes 3 seconds") and the frame index are written into the valuetext at initialisation and again on blur, so they are spoken when the thumb next gains focus, and omitted from every change while focused, which honours both sentences on the APG page (ledger row 25). The status region receives one short message on commit ("Seeked to 1 minute 32 seconds, chapter Boot"), on play and pause, and when a chapter boundary is crossed while playing, rate-limited to chapter boundaries and never per sample (R2 recommendation 11; PhET's context response), as the film's live region already does for cancel and speed (`film.rs:576-602`, `film.rs:1077`). Clock-driven `aria-valuetext` updates are debounced 300 ms and applied only while the thumb has focus; key and pointer seeks update it immediately (PhET, researcher-sighted); no `aria-atomic` clock, no assertive regions. Reasoning: the slider role already speaks its value, so a live wrapper double-announces (accessibility.build via R2); O'Hara's "fewest live regions"; the film's current valuetext repeats the total on every step, which R2 and R3 both flag. Sources: R2 finding 19 and recommendation 11, R3 priority 2. Established practice; the chapter announcement reverses my earlier draft in R2's favour.

19. Pointer. Hover peek is enabled on `(hover: hover) and (pointer: fine)` (amended 2026-09-04: the feature being gated is hovering, and `pointer` says only how precise the primary device is, so a pen-driven screen answers fine and cannot hover; the pair denies a mouse docked to a tablet, which `any-hover` and `any-pointer` would serve at the cost of enabling the peek on a touchscreen laptop, so the primary-device pair is the choice); a press without movement, on the track or anywhere on the plot, commits a seek to that x on release (SC 2.5.7's tap on the track, verified); a press that moves becomes a pending seek with a preview, committed on release and cancelled by Escape; returning the pointer within a few pixels of its origin before release shows a "release to cancel" state and cancels, which R3's expanded text calls "an extrapolation from a mobile-only feature to pointer drags, so treat it as an experiment", so it ships behind the interaction report's review; hover emits a peek snapped to the nearest sample along x within 40 CSS px, y ignored (Plot, verified); on coarse pointers there is no hover, a long press starts the pending seek with the preview above the finger (the film's `.peek` already sits above the chart, `film.rs:745`), and the iOS slide-down speed gesture is not adopted (R3). The film gains previous and next chapter buttons in its control bar as a further single-pointer alternative (R2 recommendation 6), and its native `dom.slider` control remains as the user-agent-exception fallback for touch assistive technology (agreement 15). Sources: R3 priorities 1 and 2 and dissent, R2 finding 4 and recommendation 6, SC 2.5.7. Established practice, with the snap-back marked experimental.

20. Target size and focus ring. The thumb, every mark and every chapter tick carry an invisible 24 by 24 CSS px hit rect, or, where marks sit closer than 24 px, the spacing exception is proven by the test rather than assumed; the track counts as one target under 2.5.8's spatial-selection rule (verified). The focus ring is an in-SVG `<rect>` around the thumb with `stroke: currentColor`, 2 px wide, offset 2 px outward (a 2 px inset ring fails 2.4.13, R2 finding 6), `fill-opacity` 0, shown on `:focus-visible` only, at 3:1 against the surface and a 3:1 change against the unfocused state, plus a stronger stroke on the thumb itself; no CSS outline on SVG nodes because UA outlines on SVG scale and clip in user space (R2 finding 20, R1 finding 24, researcher-sighted; APG's ring, verified); `focus({ preventScroll: true })` when moving focus programmatically; the interaction report checks that sticky page chrome never covers the thumb at either end of the track (2.4.11). Marks and chapter ticks get hover and focus styling through their parts, with focus mirroring hover (Chartability). Sources: R2 recommendations 7 and 8 and findings 5, 6 and 20, R1 finding 24. Established practice.

21. Reduced motion. Playhead position updates always happen (essential motion under 2.3.3, researcher-sighted); the transform transition, the ghost travel, travelling strip markers and any page-turn easing are disabled through the film's existing motion tokens under `prefers-reduced-motion`, so the chart and the strip agree (R2 recommendation 9); nothing else inside the SVG animates in any mode (uPlot via R3). Sources: R2 finding 7, R3 priority 3, R4 recommendation 3. Established practice.

### Colour system

22. Series palette. Tokens are `oklch()` at the computed Okabe-Ito hue angles (orange 77, sky blue 236, bluish green 166, yellow 105, blue 244, vermilion 48, reddish purple 346; R2 finding 11, reproduced), in two lightness bands per theme with one chroma ceiling (0.14 to 0.16, the largest value in sRGB gamut for every hue at both bands). Light theme: bands about L 0.55 and 0.65 on white with the WCAG 3:1 floor, where WCAG and APCA agree (3:1 is about Lc 56 to 60). Dark theme: bands about L 0.75 and 0.85 on `#2B415F` with an APCA Lc 45 floor (about 4.3:1), chosen over the bare 3:1 floor because 2 px strokes on a dark surface at 3:1 sit at only Lc 31 to 37, which is the thin-line case WCAG's own text says to exceed, while the Lc 60 floor pushes the palette to pastels and the CVD minimum to 6.6. Default charts use four series in one band (orange, bluish green, blue, reddish purple), the largest set robust in one band (37.5 normal, 12.1 protan, 15.9 deutan, 7.9 tritan); six series use the computed two-band set (orange, sky blue and reddish purple in the darker band; bluish green, yellow rendered as olive, and blue in the lighter band), which drops vermilion and black because orange and vermilion collapse under deuteranopia (5 hues in one band bottom out at 4.2 to 5.5). The present colours fail today (#0072B2 at 2.00:1 and #D55E00 at 2.68:1 on `#2B415F`, #E69F00 at 2.25:1 on white; reproduced). The exact L values are outputs of the test, not inputs. Sources: R2 findings 10, 11 and 13 and recommendation 1 (figures reproduced, ledger row 35), Okabe and Ito (verified), Datawrapper and Carbon (researcher-sighted). Our judgement, informed by R2's computations; the dark-theme floor is the one choice R2 left to the team.

23. Palette test. A Rust test over the token file, using the palette crate (`Wcag21RelativeContrast`, `Ciede2000`, `Oklch`, verified) and farg (`brettel`, verified), with the thresholds in one documented constant block labelled as project conventions and the test data generated from the tokens, not a hand-typed list (R2 recommendation 2): for every theme and each of `--op-bg`, `--op-surface` and `--op-raised`, WCAG ratio at least 3.0 for every series token, the playhead, the peek rule and the band edge, compared without rounding; at least 4.5 for every label colour against the surface it sits on (a label on the band against the band); APCA Lc computed with a pinned port cross-checked against black on white (about Lc 106), asserted at least 45 on the dark surfaces and reported below 60 everywhere; pairwise CIEDE2000 at least 10 between all series tokens in normal vision and at least 8 after Brettel simulation of protan, deutan and tritan, reporting the failing pair and condition; CIEDE2000 at least 20 from each series token to the surface; a gamut check that each `oklch()` token round-trips through sRGB without clipping; the grid token exempt from 3:1 in the default theme with the reliance on the table and tick labels stated in the test name and message, and held to 3:1 in the `prefers-contrast: more` variant; a few units of slack noted because Brettel and Machado differ at the margins (R2 finding 14). The test's documentation states that the CIEDE2000 floors are conventions from Palettailor and PaletteGuard, that the APCA levels are author drafts, and that WCAG 3's draft names no algorithm (verified). Sources: R2 recommendation 2 and findings 12 to 14, ledger rows 12, 16, 17, 31, 35. Test design our judgement; floors from the cited conventions.

24. Dashes, markers and labels. Series 1 solid; series 2 to 6 take R2's dash table (`8 4`, `2 3`, `8 4 2 4`, `12 4`, `4 2 4 6`), scaled by stroke width, with `stroke-linecap: butt` so the pattern survives at 2 px (R2's open question); strokes 2 px for series and playhead, 1.5 px for the band edge only if the band is labelled or its fill passes 3:1; each series gets a direct end label at its last point, right of the plot, at 4.5:1 and at least 12 px, with a `paint-order: stroke fill` halo in the surface colour 3 px wide so the label's local background is always the surface; labels placed greedily with a 12 px minimum separation and shifted within the plot band before any is dropped; a legend only when an end label cannot be placed; markers at sparse samples only where a series has no end label and in forced-colours and high-contrast modes (the markers conflict); the time readout on the axis band with the same halo, beside the thumb while scrubbing, never over the series (the film's `head-t` moves to the axis band in phase 0); mark labels along the bottom edge with greedy removal, the mark nearest the playhead winning; a 1 px surface-coloured gap wherever the band meets a series line or the playhead (R2 recommendation 4, Chartability's 1 px rule); no text under 12 px anywhere in the chart. Reasoning: 1.4.1 forbids colour as the sole cue (researcher-sighted); Okabe and Ito (verified), Datawrapper, the FT and Datadog's last-point labels (researcher-sighted); the halo turns "label over series" into a label-over-surface problem the palette test covers. Sources: R2 recommendations 3, 4 and 14, R3 priority 3, R4 recommendation 4. Established practice; the marker rule is ours.

## Phase 2 close-out (2026-09-04)

Phase 2 delivered the element. In `op-chart`: the JSON data block of
decision 1 read by a dependency-free reader shared by the build and the
browser, a stable FNV-1a content hash, the `</script` escape, gaps drawn
as path breaks with isolated samples marked so they stay visible, a layout
sized to any box in CSS pixels with non-scaling strokes, per-column
decimation past the plot width, alternating classes on time labels and a
group around the chapter cues so a container query can thin them. In
`op-webc`: JavaScript accessor properties declared per element, with the
upgrade-property replay, so `data` and `forElement` exist. The
`opt-film-time` detail is now `{ time, duration, playing }`, read by the
machine and the chart. `<opt-chart>` itself: intake from the block or the
`data` property, hydration of a declarative root whose `data-hash` matches
(exposed as the `hydrated` state), binding through `for` in the tree scope
and the document with a document-level fallback listener, the `following`
and `playing` states, the per-tick transform update coalesced into one
animation frame, and a resize observer that re-lays the chart out at the
measured width. `op-pages` lowers `<opt:chart>` to a declarative shadow
root holding the finished SVG, a caption with a generated summary and the
data as a table behind a disclosure, with the block and its hash beside
it. The docs page at `/component/chart/` carries a film, the chart and a
machine on one clock, and the interaction report gained a chart kind:
static captures with scripts disabled at 640 and 360 px, hydration, a full
play against the film's clock, and resize.

Departures and decisions made while building. The pre-render ships two
SVGs, a wide one at `initial-width` and a narrow one at 360 px switched by
a container query at 532 px, because a single 640 px pre-render scaled to
a 360 px viewport puts its 12 px labels at about 6 px, under the 10 px
floor the conflict on pre-render width set as the trigger. On upgrade the
element keeps whichever pre-rendered SVG already fits the measured width
within a pixel and removes the other, so the build's markup survives on
the page it was drawn for; at any other width it draws one live SVG at the
measured width and the pre-render is gone one frame after upgrade. The
aspect ratio applies to the SVG's box rather than the host, since the
caption and the table share the shadow root, and the `ratio` attribute is
written into the stylesheet as the fallback of `--op-chart-ratio` so the
viewBox and the CSS box agree. The chart element's text is 12 px per
decision 24 while the film's own chart still uses 11 px; the two meet when
phase 4 restructures the film's chart. The value domain comes from `y`, else
the film's percent scale when every series is in percent and its values fit
that scale, else the data's range padded by four percent; marks and the band
are parsed, validated, summarised and tabled but not yet drawn. The
`data-series` attribute of decision 6 waits for phase 3, which brings the
hit-testing it serves. The element's
SVG carries `role="graphics-document"` labelled by the caption's title
rather than the renderer's slider markup, which stays on the film's chart
until phase 4 builds the thumb group. The renderer now emits `part` on the
svg, the playhead group and every series path (decision 6), and the film's
snapshots also moved for the alternating tick-label class, the chapter
group and those parts, none of which the film styles, so its rendering is
unchanged. Grid lines take `shape-rendering: crispEdges` (decision 11); the
swatch keeps it too because the interaction report samples colours there.
The pre-rendered table carries chapter rows as well as mark and band rows,
with the chapter also named in a column of every sample row. The hash on
the element covers the block text as emitted, after the `</script` escape,
which is the text the browser reads back. Setting the `data` property
removes `data-hash` and clears `hydrated`, so a later reconnect cannot
hydrate stale geometry, and an invalid value leaves the wiring in place so
a later valid one recovers. The renderer's group order is asserted as the
emitter's real order (axes, marks, series, track, cursor, playhead) rather
than the list in decision 12, which is a separate snapshot rewrite. The
site stylesheet carries `:not(:defined) > template[shadowrootmode]`, with
the caveat that a template's children are inert by construction, so the
rule only helps engines that expose them; declarative shadow roots are
Baseline 2024 and the real fallback is that the markup exists at all. In
the report, the playhead is judged against the chart's own readout with a
2 px tolerance (the readout rounds to 0.01 s), the readout may never run
ahead of the film's clock, and it may trail it by at most one frame, where
the frame interval is measured from the film's own readout changes during
the recording rather than assumed.

Firefox on ppc64le. atlas runs Ubuntu 24.04 on POWER, where no Firefox
snap exists; `firefox-esr` 140.15.0esr from the Mozilla team PPA was
installed and driven headless. None of the site's wasm runs there, so the
film above the chart and the site chrome are absent, and the pre-rendered

every tick label, at 360 px the narrow variant with alternate labels
hidden, both with the caption, the summary and the data table. The

`chart-element/atlas-ppc64le-firefox-360.png`.

kept for the inspector, so every figure is larger than what a stripped
build would ship): the renderer, `op_chart::render::render` with everything
it retains, is 13.1 KB, under the 20 KB gate R4 set, after the two generic

## Phase 3 close-out (2026-09-04)

Phase 3 gave the chart its intents. Every gesture and key asks the film for
a time, in seconds; the chart still moves only when a tick comes back, so
one clock stays in charge. `op-chart` gained `Layout::nearest`, the sample
under a pointer within a radius, and a final `targets` group of 24 by 24 px
rects that are hit without being painted at all, one per mark and one per
chapter after the first. A transparent fill would still be a painted
rectangle for forced colours and print to undo, so the rects take
`fill="none"` with `pointer-events="all"`. They carry the cue in
`data-cue` rather than in a class, because the first attempt reused the
painting classes and every hit target drew itself, including an opaque box
over the track on any film with two chapters; a test now enumerates the
stylesheets' selectors and fails if a target can match one. Their rows are
clamped inside the drawing box, since a rect that hangs past it is clipped,
and clipped geometry is not hit-tested, which had quietly cut the chapter
targets to 24 by 20. Nothing reads the group yet: decision 20's focusable
marks and chapter ticks are phase 4, and until then the targets only take
the pointer away from what is behind them.

The element gained the pure decisions behind the gestures, `snap`,
`key_intent` and `pointer_phase`, each tested on both sides of every
threshold, and the wiring that turns them into `opt-chart-seek`,
`opt-chart-peek` and `opt-chart-toggle`, with the `peeking`, `pending` and
`cancelling` states. Hover is gated on `(hover: hover) and (pointer: fine)`
per the amendment to decision 19. The coarse path is decided per gesture
from the pointer's own type rather than from the device, so a finger on a
touchscreen laptop gets its long press and a mouse on a tablet does not.
`End` and the digits use the announced duration rather than the axis end,
which the schema lets differ. The film applies the three intents from any
chart that names it, reading the source from the event's composed path
rather than from the retargeted target, which had misrouted a chart behind
a third element's shadow root; its control bar gained previous and next
chapter buttons that share the keys' own stepping.

Marks and the band are drawn at last. They were parsed and validated in
phase 2 and reached nothing, so the docs promised cues that did not exist.
A mark is a rule with a bottom-edge label, the band a rect behind the
series with its own label and a one pixel surface stroke where it meets a
line, which is now a real rule in both stylesheets rather than the inert
attribute the first attempt shipped with a test asserting it. Both new
label classes gained their own rules and the halo every label over the plot
carries, having painted in the user agent's black with none; and the
track's own wash is `peek-band` now, because two rects sharing the class
`band` meant a query for one could take the other. The top row,
the chapter and band labels, goes through one placement pass with the end
labels' column reserved, and a label that cannot be placed is dropped: the
film's own flight fixture is the first casualty, showing its last
chapter's rule without the word, which is the intended trade against text
printed over text.

The interaction report drives all of it with real input on the synthetic
clock: the chart kind went from 26 checks to 99. A tap seeks where it
lands, a drag previews without moving the clock and commits on release,
Escape mid-drag leaves the clock where it was, every key moves the clock by
the amount the page's own data block predicts, Space plays and pauses, keys
struck while the focus is elsewhere reach the element and are refused, and
a coarse long press under touch emulation aims and commits. Hover is driven
for real: headless reports no pointer by default, but the Blink settings
`primaryPointerType=4,availablePointerTypes=4,primaryHoverType=2,availableHoverTypes=2`
give it a fine hovering one, and `Emulation.setTouchEmulationEnabled` still
overrides that to coarse, so both branches run in one pass. The hover edge
opens with a hard precondition, so it fails rather than degrading if a
browser ever reports no pointer again.

A second pointer going down takes the press over, the press it replaces is
ended rather than left lying, and a release carried by any pointer but the
live one is ignored, so a two-finger scrub commits under the finger that
owns the gesture and nothing is left set behind the other. An edge drives
two touch points in both orders and measures it, including the pointer
capture moving with the press.

Two defects the harness found in the element, neither visible to a unit
test. The long-press wake-up was armed for exactly its own threshold, and
the phase compares against that same number, so on a synthetic clock the
coarse gesture armed or did not depending on rounding, failing about one
run in three; it now wakes a millisecond later. And the snap-back cancel,
added because decision 19 asks for a held state rather than an event, made
a long press cancel itself: a press that aims without moving sits in the
cancel band from the first instant. Coming back now means having left, and
`Down::travelled` records it.

Two defects in shipped work came out of drawing the palette specimen, which
is what looking at a thing in use is for. The peek rule was painted with
the muted text colour while `--op-peek` sat declared, registered, blended
by the theme transition and held to a contrast floor by the palette test,
drawing nothing; the two carry the same value in both themes, so it looked
right. And the forced-colours and print blocks were interpolated where
eight later rules at equal specificity overrode them, so on a forced
palette the playhead, its dot, its readout, the track, the played bar, the
chapter tick and the peek rule all kept their theme paints and the band
stayed a wash instead of becoming an outline. Phase 1's own checks never
saw it: they sampled the series strokes, the markers, the grid and the end
labels, every one of which is painted before the shared blocks and so was
never in doubt. The blocks now sit after the last rule that paints a token,
a test asserts that nothing written after them repaints what they map, and
the report reads the computed paints of the playhead, the track and the
peek rule under a forced palette.

What phase 3 does not do. The chart is focusable and operable, and it
announces no value: the aria value attributes belong to the range roles,
not to the `graphics-document` the svg carries, so writing them there
announced nothing. It also has no summary and no instructions
line, so a reader who focuses it is told neither what it holds nor that it
answers keys. Decisions 15 and 18 build the thumb group that can hold a
value and the described summary that says what the chart is, and that is
phase 4's work, along with decision 17's `step` attribute, `delegatesFocus`
and the roving tabindex between the thumb, the marks and the chapter ticks. The snap-back ships as the experiment the
research note called it, marked as such on the docs page.

## Phase 4 close-out (2026-09-05)

Phase 4 gave the chart the structure decision 15 asks for. The host is a
group labelled by its visible title and described by its summary and a
visible instructions line naming the keys. The svg stays a
`graphics-document`; the grid, the axes, the ticks, the band and the
decorative marks sit in a group hidden from the accessibility tree; each
series is a `graphics-object` named with its label, its sample count, its
range and its span; the marks and the chapters are groups of buttons
wrapped around the hit rects phase 3 emitted; and the playhead is the one
slider, carrying `aria-valuenow` and a spoken `aria-valuetext`. The svg is
never a slider and never an image, and the readout inside the thumb is
hidden from the tree, because Chrome exposes it as a text child and decision
15 exists to stop the time being read twice.

The film's own chart had been a focusable slider whose value never changed
since phase 2. It is now a labelled document with a visible title, hidden
decoration, named series and a decorative playhead, and the film's native
range input is the single slider a reader tabs to. Its text is 12 px, so
the film and the element agree at last.

Announcements follow decision 18. A status region, present from the first
render, speaks on a committed seek, on play, on pause and when a chapter
boundary is crossed during playback, and on nothing else: no peek, no
pending, nothing assertive. The spoken value carries the duration and the
frame index while the thumb is unfocused, so they are heard when it next
gains focus, and drops them while focused; a clock tick writes at most
every 300 ms and only while focused, while a key or pointer seek writes at
once, in the same frame it is emitted. The film's own control follows the
same rules, reusing the chart's decision rather than a second copy, and its
region and its control now spell one instant the same way.

Decision 20's ring is an in-SVG rect two pixels outside the thumb, painted
with `currentColor` so a forced palette carries it without a mapping of its
own, shown on `:focus-visible` only, and computed from the tokens at 3.15
to 1 against the dark theme's surface and 4.54 to 1 against the light
theme's. No CSS outline touches a node of the
drawing: the shared base stylesheet reaches every focusable node in the
shadow root, and the guard that was meant to forbid that could only see
selectors naming an emitted class, so it saw nothing. The cues take a
painted indicator instead, shared byte for byte with the film, which reads
the rules out of the element's own source so the two cannot drift.

The roving of decision 17 is real rather than nominal: Down from the thumb
enters the cues, the arrows step in time order, Enter or Space seeks to the
focused cue, and Up or Escape returns. It walks only the cues the drawing
shows, because below the width that hides the chapter bar the earlier
version moved the tab stop onto a hidden node and left the widget with no
reachable stop at all. The `step` attribute and `delegatesFocus` are in
place, and the element no longer trusts the engine's choice of delegate:
Chrome puts a delegated focus on the svg rather than the thumb, so an
engine-placed focus is moved to the stop while a focus the reader put on a
cue or on the data table's disclosure is left alone.

What driving a browser found that no unit test could. A pause was never
broadcast, so no follower could announce it. The value on a committed seek
was a frame late. Every path
that seeks repeatedly was announcing repeatedly: a chart scrub, a native
range drag, and a drag entering the chart without its own press are each
one gesture and now speak once, when they settle. Two more came from a
probe rather than from a check, and are fixed with the tests that hold them
rather than with a witness: a re-layout could leave the shadow root with no
active element, and the report's own re-layout edge still accepts the focus
landing outside the element, so what is guarded is the restore rather than
the loss. One came from reading the code across a seam: the film had
inherited the chart's cue defect, drawing the same buttons from the same
renderer while its own key handler never asked what held the focus, so
Space on a cue played the film.

The report drives all of it: 308 checks over 20 controls, the chart at 146
and the film at 54, with the accessibility tree read once per edge and
everything derived from it, the ring measured in pixels and in computed
values, the status region read after each event that must speak, the value
text witnessed at dispatch time rather than after a frame, and the target
sizes measured against the spacing exception.

Carried into later phases, recorded rather than hidden. Shift and Tab
return to the thumb rather than to the cue the stop sat on, which is where
Chrome's delegation lands. The embedded case, where a chart inside a film
yields the slider, is implemented and tested and remains unreachable at
runtime, because the film draws the renderer's SVG into its own root rather
than nesting the element. The `aria-describedby` relationship has no browser
witness yet. And two checks stand as guards rather than as proof: one
sub-check of the narrow-width roving passed against the unfixed build,
because the state it guards is real but Chrome repairs it before the next
frame, and the film's cue press has no pre-fix evidence at all, because the
rebuild replaced the tree before that run could be staged and no such
evidence was made up to fill the gap.

## Phase 5 close-out (2026-09-05)

Phase 5 gave decision 14 its measurement. The emitter had reserved 6.5 px
a character, which is right for no string the chart draws. `op-assets`
now reads the served woff2 with ttf-parser and emits an advance table per
weight into `op-chart` as a generated source, so the renderer measures
without a font file, a build script or a dependency of its own. A test
regenerates the table and compares it byte for byte, and a second test
measures the strings the chart draws straight out of the woff2 again and
asks the two for the same number. The table records the family, weight
and style it was read from, so the element can ask a browser for exactly
that face and the check cannot drift from the widths it stands in for.

With real widths the tick labels no longer need the `alt` class or the
container query that hid every second one below 480 px. Every row of
labels now goes through one function, and the time labels are thinned by
whether a label clears its neighbour rather than by counting. Where the
box has room every tick keeps its label; where it does not, the ones that
cannot clear are dropped and the survivors stay on their own rules, which
a test proves by comparing each one's x against the rule it belongs to.
`textLength` is emitted only on the gridline values, which must fit the
axis gutter.

The runtime fallback is decision 14's last clause. The element asks
`FontFaceSet.check` for the face the tables record and, when it is
missing, waits for `fonts.ready`, measures its own strings with
`measureText` on an offscreen canvas and re-lays out once against the
ratio it finds. The decision is a pure function of two facts, and its
flag goes up when the element leaves to wait rather than when the
measurement lands, so a tick, a re-render, a theme change or a resize
arriving in between is told to wait instead of starting a second
measurement.

What the phase actually established is larger than the stories asked for,
and is written up in `font-metrics-2026-09.md` with its sources. In
short: a De Bruijn sweep of order 2 over the 95 characters the tables
cover proved them exact to inside the engine's own sixty-fourth-pixel
grid over all 9025 ordered pairs; kerning tightens far more often than it
loosens, so the summed advances are always the wider number and a label
placed by them is reserved generously rather than crowded; a shaper
reproduces the browser to 0.0074 px; and reading GPOS by hand is a trap,
because OpenType applies the first matching subtable within a lookup and
the obvious class expansion gets four pairs wrong.

Three checks watch it from outside. The specimen sheets set every string
the chart draws with the face's own metrics drawn over them, which
settles what a number cannot: ink is narrower than advance by the side
bearings, so the two are not comparable and the sound comparison is the
browser's own laid-out width. The label check reads the chart's labels
out of the built site's own page at 900 px, at 360 px, and at 360 px
reached by resizing, measures each box from the glyphs the browser laid
out, and finds nothing overlapping at any of them, the closest being 1.4
px apart. With the served faces blocked, all five gridline values stayed
pinned to their `textLength` slot to the hundredth of a pixel. And the
gate now emits every page twice and requires the same bytes, since the
pre-rendered chart is what a reader without scripts is served and every
step that produces it is a pure function.

Two things were got wrong first and are worth recording. `:state(hydrated)`
is not the signal for "the element drew this": the element only reports it
when it adopts the pre-render it was served, and when the served one is
the wrong width it draws its own while the state stays false. And a
comparator that prints the first 160 characters of a differing line tells
a reader nothing when the line is 22,000 characters of markup, all of
which is identical up to the change.

One thing the phase found and did not fix. The specimen and sweep runs
drive Chrome's new headless, which keeps a glyph's advance; the
interaction report drives chrome-headless-shell, whose default rounds
every advance to a whole pixel. Nothing published is wrong, but the two
harnesses do not measure text the same way, and aligning them changes
rendered pixels, so the frame comparator's baselines move in the same
commit. That is a deliberate change to make on its own, not a side effect
of the first text check that needs it.
