# Facet 4: Rendering technology and the Rust toolchain for opt-chart

All sources were fetched and read on 2026-09-03. Crate versions and dates come from the crates.io API queried that day; web-sys facts were checked against the local web-sys 0.3.104 source in the cargo registry.

## Summary

Classed SVG stays the right choice. A line series is one `<path>` node at any point count: in a July 2026 headless-Chromium benchmark a 100,000-point line rendered in 41 ms as SVG against 29 ms as canvas, while a 20,000-point scatter became 20,102 DOM nodes and took 233 ms against 59 ms. SVG hurts only when marks become nodes or when hundreds of elements are edited every frame; our chart edits three. A GPU path makes no sense: Vello classic needs compute shaders, WebGPU is Nightly-only in Firefox on Linux (which includes every ppc64le user), and even vello_hybrid's leanest WebGL2 build is 1.9 MB of wasm against a 240 KB site. No Rust chart crate emits token-classed SVG; poloto is the only classed one and has had no release since 2023-07-09, so it is a design reference, not a dependency. Use no runtime crates for emission, port d3-ticks (or the new axis-labels port of R's labeling package) for nice ticks, and consider kurbo only for op-webc machine edges after measuring its wasm cost. Lay out in CSS px with the viewBox equal to the host box, because SVG 2 scales px and em text alike under a stretched viewBox. Per tick, set `transform` on a playhead group, the label text and the played-bar width, coalesced into one requestAnimationFrame, and never rebuild series paths. Forced-colours mode leaves SVG fill and stroke literals untouched (UA rule `svg|svg { forced-color-adjust: preserve-parent-color }`), so the class stylesheet must map to system colours explicitly and series must differ by dash and marker, not colour alone. Measure text from build-time glyph advance tables made with ttf-parser, with canvas `measureText` after `fonts.ready` as the fallback. Declarative Shadow DOM (Chrome and Edge 111, Safari 16.4, Firefox 123, February 2024) lets op-pages pre-render the chart; the wasm element hydrates via `Element::shadow_root()` because web-sys 0.3.104 has no ElementInternals binding. Test with insta snapshots, resvg 0.48.1 pixel renders (reproducible across platforms) and CDP screenshots under emulated media features.

## Findings

### Question 1: Rust crates

1. poloto 19.1.2, released 2023-07-09, no release since; 868,791 downloads; GitHub shows 164 stars, 25 open issues and one substantive author (tiby312, 1,464 of 1,465 contributions) (https://crates.io/crates/poloto, https://github.com/tiby312/poloto-project). It is the one crate designed for what we want: "A simple 2D plotting library that outputs graphs to SVG that can be styled using CSS", styled "either directly in the SVG, or from inside of html with an embedded svg", which "allows the user to dynamically match the svg to their website's theme". Its class scheme is worth copying: `.poloto_line`, `.poloto_scatter`, `.poloto_histo`, `.poloto_text`, `.poloto_background`, `.poloto_ticks`, `.poloto_imgs`, `.poloto_plot` versus `.poloto_legend`, `.poloto_name.poloto_x`, and `.poloto0`, `.poloto1` per-plot indices, so one rule such as `.poloto_line.poloto_imgs.poloto_plot{stroke:purple;stroke-dasharray:40px}` restyles a series. Theming is `poloto::render::Theme::light()` or `dark()` plus raw CSS appended through the tagu 0.1.6 (2023-07-11) XML builder; ticks come from `poloto::ticks::from_iter(...)` with `.with_tick_fmt(...)`; a viewBox width is set with `poloto::header().with_viewbox_width(1200.0)`. What it does not offer: maintenance, a way to emit our token names, or any runtime update model (it renders a whole document).

The API is colour-value based (`&RED`, `WHITE.mix(0.8)`, `("sans-serif", 50).into_font()`), so its SVG carries colour literals and there is no class hook; the wasm story is the HTML5 canvas backend (`CanvasBackend`) plus a wasm demo; the bitmap backend needs freetype and fontconfig. A wasm binary size figure was not found in the README or crate pages.

4. resvg 0.48.1 and usvg 0.48.1 (2026-08-02, MSRV 1.85.0), tiny-skia 0.12.0 (2026-02-02) (https://crates.io/crates/resvg, https://github.com/linebender/resvg). resvg renders the static SVG subset only ("no `a`, `script`, `view` or `cursor` elements, no events and no animations"), has "around 1600" SVG-to-PNG regression tests, is "written completely in Rust", works "everywhere where you can compile the Rust itself, including WASM", and is reproducible: "if you render an SVG file on x86 Windows and then render it on ARM macOS - the produced image will be identical. Each pixel would have the same value." Parsing (usvg) and rendering (resvg) are separate crates. It has no native text rendering and loads fonts through fontdb. The unsupported-features document lists SVG font elements, `use` of external files and attributes such as `direction`, `unicode-bidi`, `font-size-adjust`, `font-stretch`; it says nothing about CSS custom properties or `var()`, so pixel tests must feed it literal colours (https://github.com/linebender/resvg/blob/main/docs/unsupported.md).

Vello family. vello 0.10.0 (2026-08-14, MSRV 1.88), vello_cpu 0.2.0 and vello_hybrid 0.2.0 (2026-08-07, MSRV 1.88), vello_svg 0.10.0 (2026-07-19), peniko 0.6.1 (2026-05-15) (https://crates.io/crates/vello, https://crates.io/crates/vello_hybrid). Vello CPU", with mask layers, complex filter graphs and some blend modes still panicking, experimental glyph caching, and "Some failures panic instead of being reported"; feature `webgl` enables a native WebGL2 backend with GLSL shaders (https://crates.io/crates/vello_hybrid). Verdict for a line chart: the smallest GPU build is eight times our whole site wasm, requires WebGL2 or WebGPU, loses DOM hit-testing, CSS theming and accessibility for free, and buys nothing, since a polyline is one path node.

### Question 2: Platform facts

9. SVG versus canvas, measured. The ApexCharts benchmark of 2026-07-20 rendered a seeded single-series random walk into an 800 by 400 container with animations disabled, in headless Chromium 147 driven by Playwright on an Apple M4 Pro, timing from chart construction to the library's completion signal plus a double requestAnimationFrame, five-trial medians in fresh contexts, with a stated resolution floor of about 16.7 ms (https://apexcharts.com/blog/javascript-chart-library-benchmark/). Line, milliseconds at 1k/10k/50k/100k points: uPlot 10/9/9/9; ApexCharts canvas 16/18/26/29; Chart.js 16/19/24/33; ApexCharts SVG 15/18/31/41; ECharts 20/25/35/47; Highcharts 18/28/63/107; Recharts 24/47/138/264. Scatter at 5k/20k/50k: Chart.js 24/47/89; ApexCharts canvas 29/59/120; ApexCharts SVG 64/233/527; Recharts 210/698/1,820; ECharts 125/466/1,923. At 20,000 scatter points ApexCharts SVG created 20,102 DOM nodes, Recharts 60,082 (three per point), the canvas renderer 104. Replacing a 10,000-point line took 16 ms for most libraries; replacing a 50,000-point line ran at about 2,560 updates per second in uPlot, 256 in ApexCharts canvas, 232 in Chart.js, 13 in Highcharts. Their reading: "SVG was never the problem for lines", "Node-per-point shapes are where SVG hurts", "Below 10,000 points, do not choose a library on speed", and downsample "to roughly the visible pixel width" above a few hundred thousand points. Their March 2026 guide sets "a rough SVG ceiling" at "a few thousand individual marks per chart", keeps lines and areas in SVG at "any realistic point count", and prefers SVG for per-point interaction, accessibility, print and export (https://apexcharts.com/blog/svg-vs-canvas-charts/).
10. Horak, Kister and Dachselt, "Comparing Rendering Performance of Common Web Technologies for Large Graphs" (2018) built the same tree visualisation in D3/SVG, plain Canvas and PixiJS/WebGL, about 20 graphical elements per node, and replayed a fixed 20-second zoom-and-pan sequence on a Windows 10 laptop (i7-7500U, integrated graphics), logging FPS in the browser devtools (https://imld.de/cnt/uploads/Horak-2018-Graph-Performance.pdf). Findings: "performance losses started to occur above 400 nodes (ca. 8,000 elements) for all three technologies. SVG and Canvas perform almost equally"; WebGL only dropped when it drew text (400,000 nodes at 50 FPS without text); "For SVG and Canvas, a rough limit for a fluid interface is 10,000 graphical elements"; and in Firefox, "when starting to perform the interactions, the browser internally applied style changes, which blocked interface updates for a few seconds". This is an interaction (zoom and pan) benchmark on 2018 hardware; the element count, not the data size, is the variable.
11. Per-frame edits. Chapparam's telemetry study (2026-06-18) measured main-thread work per frame while N series changed every frame: at N=1, 0.45 ms (SVG through React), 0.22 ms (imperative SVG), 0.07 ms (canvas); at N=50, 3.84/1.86/0.39 ms; at N=200, 10.51/5.18/1.07 ms. Imperative SVG first dropped frames near N=600 (46 fps, 14.5 ms of work) and canvas near N=600 too but bound by paint of a 2880 by 840 surface at DPR 2 (2.3 ms of script). Under a 6x CPU throttle on an i9: N=50 gave 36.7/57.4/60 fps and N=200 gave 11.6/18.8/60 fps. Its remedy for oversampled telemetry is decimation, "bucket the buffer by pixel column and draw the min and max of each column", explicitly not LTTB, which can drop a single-sample spike (https://dev.to/jaya_chapparam/svg-renders-telemetry-at-60fps-we-use-canvas-anyway-and-here-is-the-measured-reason-15gc). Our per-tick edit touches three elements, two orders of magnitude below the point where imperative SVG struggled even when throttled.
12. Custom properties inside shadow SVG. CSS Scoping Level 1 section 3.3.2: "The top-level elements of a shadow tree inherit from their host element." (https://www.w3.org/TR/css-scoping-1/). Custom properties "are subject to the cascade and inherit their value from their parent", and "Variables do not work inside media queries" (https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascading_variables/Using_CSS_custom_properties). Together these mean every `--op-*` token on `:root` reaches the SVG inside the shadow tree without any bridging. `@property` (Baseline 2024, since July 2024) can turn inheritance off; `syntax` and `inherits` are mandatory, `initial-value` must be "computationally independent" (`3em` is invalid), the last registration wins and a JavaScript registration beats CSS (https://developer.mozilla.org/en-US/docs/Web/CSS/@property). `currentColor` "represents the value of an element's color property" and, used as the value of `color` itself, takes the inherited value (https://developer.mozilla.org/en-US/docs/Web/CSS/color_value). The shadow tree also inherits `dir` and `lang` from its host (https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM). How `url(#id)` references such as `clip-path` resolve across shadow trees is not addressed in the scoping spec (and the drafts.csswg.org URL now redirects to a "CSS Shadow" module), so I treat per-instance id prefixes as required rather than optional.
13. Presentation properties, all from MDN. `paint-order` is Baseline 2024 (since March 2024); default order is fill, stroke, markers, so `paint-order: stroke fill` draws the stroke behind the fill, the standard text-halo technique; it is inherited (https://developer.mozilla.org/en-US/docs/Web/CSS/paint-order). `vector-effect="non-scaling-stroke"` has been available across browsers since July 2020 and makes "the stroke width ... not dependent on the transformations of the element ... and zoom level"; the spec's `non-scaling-size`, `non-rotation` and `fixed-position` "have no implementations and are considered at-risk" (https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/vector-effect). `text-rendering` (since January 2020) is an SVG property that Gecko and WebKit also apply to HTML; `optimizeSpeed` disables kerning and ligatures; `geometricPrecision` exists for SVG so that scaled text is not rounded to the platform's nearest integer font size ("stair-step scaling"), but "WebKit precisely applies the specified value, but Gecko treats the value the same as optimizeLegibility" (https://developer.mozilla.org/en-US/docs/Web/CSS/text-rendering). `shape-rendering` (since January 2020) applies to circle, ellipse, line, path, polygon, polyline and rect, is not inherited, and `crispEdges` "may also adjust line positions and line widths in order to align edges with device pixels" while skipping anti-aliasing (https://developer.mozilla.org/en-US/docs/Web/CSS/shape-rendering). `<foreignObject>` has been available since July 2015; its x, y, width and height are geometry properties in SVG 2 and the XHTML namespace may be omitted inside HTML documents (https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/foreignObject). The CSS `d` property (`d: path("...")`, path data in pixel units) is "Limited availability", not Baseline; Motion's guide adds that Safari "doesn't support the `d` property as a style at all" (https://developer.mozilla.org/en-US/docs/Web/CSS/d, https://motion.dev/docs/svg-animation).
14. Forced colours, the specification. CSS Color Adjustment Level 1 section 3.1: "When forced colors mode is active and forced-color-adjust is auto on an element, the <color> components of all properties on the element are force-adjusted to the user's preferred color palette." The listed properties include `fill` and `stroke` alongside `color`, `background-color`, `border-color`, `outline-color`, `stop-color`, `flood-color`, `lighting-color`, `caret-color`, `accent-color`, `scrollbar-color`, `text-decoration-color`, `text-emphasis-color` and `-webkit-tap-highlight-color`; "For each <color> component of a property, if its computed value is a color other than a system color, its used value is instead forced to a system color", so author-specified system colours are kept. Section 3.2 defines `forced-color-adjust: auto | none | preserve-parent-color` and gives the UA stylesheet: `@namespace "http://www.w3.org/2000/svg"; svg|svg { forced-color-adjust: preserve-parent-color; } svg|foreignObject { forced-color-adjust: auto; }`. Section 6 notes that forcing happens at used-value time because "Preserving system colors as keywords until actual-value time would break a significant amount of deployed script" (https://drafts.csswg.org/css-color-adjust-1/). `preserve-parent-color` means: "if the color property inherits from its parent (i.e., there is no cascaded value or the cascaded value is currentColor, inherit, or another keyword that inherits from the parent), then it computes to the used color of its parent's color property. In all other cases, it behaves the same as none"; MDN rates `forced-color-adjust` as "Limited availability", not Baseline (https://developer.mozilla.org/en-US/docs/Web/CSS/forced-color-adjust).
15. Forced colours, in practice. Because the UA rule opts the whole inline `<svg>` subtree out (the property inherits), fill and stroke literals inside a chart are not replaced. Microsoft's 2020 Edge post: "Forced color modes do not adjust SVGs: these can be very complex documents, and the web developer has better insights than the platform", so use `currentColor` on fills and strokes so "the correct color propagated to the SVG ... automatically in forced color modes" (https://blogs.windows.com/msedgedev/2020/09/17/styling-for-windows-high-contrast-with-new-standards-for-forced-colors/). Sarah Higley: "The SVG fill and stroke properties are exceptions to the rule that WHCM overrides all colors. SVG colors will be left as-is" (https://sarahmhigley.com/writing/whcm-quick-tips/). CSSence (2024): "most other colors are replaced, except for SVG's fill and stroke", "Only CSS system colors are kept", background images from `url()` are kept while gradients are removed, and `transparent` borders become visible text-coloured lines (https://cssence.com/2024/forced-colors-mode-strategies/). Polypane: forced colours "keeps your inline images and SVG icons intact, including their colors", recommends `@media (forced-colors: active) { svg { stroke: CanvasText } a svg { stroke: LinkText } button svg { stroke: ButtonText } }` or `currentColor`, and records that "In Chromium versions between 89 and 102 there was an error where this didn't happen, but that has been resolved" (https://polypane.app/blog/forced-colors-explained-a-practical-guide/). Melanie Richards explains the cause: the CSSWG moved forcing from computed-value to used-value time, which made `currentColor` inherit the parent's pre-forced colour (visible in Edge 96), and `preserve-parent-color` was added and applied through the UA rule quoted above, replacing an earlier `forced-color-adjust: none` on svg (https://melanie-richards.com/blog/currentcolor-svg-hcm/). MDN's `forced-colors` page (Baseline since September 2022) adds the special cases: `box-shadow` and `text-shadow` forced to none, non-url `background-image` to none, `color-scheme` to `light dark`, `scrollbar-color` to `auto`; browsers draw text "backplates"; `forced-color-adjust: none` disables both forcing and the backplate; `prefers-color-scheme` is derived from the lightness of `Canvas` (https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors). Consequence for us: a chart styled by tokens will keep its theme colours in forced-colours mode, which can be invisible against the forced `Canvas`; the fix is explicit system colours in a `forced-colors: active` block, not `currentColor` tricks, because grid, series, band and playhead need different roles.
16. Related preferences. `prefers-contrast` (Baseline since May 2022) has `no-preference`, `more`, `less` and `custom`, where `custom` "will match the color palette specified by users of forced-colors: active"; MDN's example turns a dashed outline solid under `more` (https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-contrast). The current system colour keywords are `AccentColor`, `AccentColorText`, `ActiveText`, `ButtonBorder`, `ButtonFace`, `ButtonText`, `Canvas`, `CanvasText`, `Field`, `FieldText`, `GrayText`, `Highlight`, `HighlightText`, `LinkText`, `Mark`, `MarkText`, `SelectedItem`, `SelectedItemText`, `VisitedText`; older ones such as `WindowText` are deprecated (https://developer.mozilla.org/en-US/docs/Web/CSS/system-color). For print, `print-color-adjust` is Baseline 2025 (since May 2025); the default `economy` lets the browser drop backgrounds and recolour text for paper, `exact` asks it not to, and user agent print options still override (https://developer.mozilla.org/en-US/docs/Web/CSS/print-color-adjust); print styles go in `@media print` or a `media="print"` sheet, with `@page` and the `beforeprint` and `afterprint` events available (https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_media_queries/Printing).
17. WCAG. 1.4.1 (Level A): "Color is not used as the only visual means of conveying information ... or distinguishing a visual element"; the understanding text names "Mary's sales are in red, Tom's are in blue" as the failing pattern and accepts a lightness difference of at least 3:1 as a second cue (https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html). 1.4.11 (Level AA) requires 3:1 for "Parts of graphics required to understand the content", thresholds are not rounded (2.999:1 fails), and "particularly thin lines and shapes ... may be rendered ... with a much fainter color", so authors should "avoid particularly thin lines and shapes, or ... use a combination of colors that exceeds the normative requirements" (https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html). Dash patterns are the obvious non-colour cue for series; they do not change contrast maths but they thin the visible ink, which argues for 2 px strokes or heavier.

### Question 3: Build time versus runtime

18. Declarative Shadow DOM support and semantics. Can I use: Chrome 90 to 110 partial (old `shadowroot` attribute), 111 onward supported; Edge 91 to 110 partial, 111 onward; Safari 16.4 onward; Firefox 123 onward; Opera 97 onward; Samsung Internet 22 onward; Opera Mini never; global usage 94.27% (https://caniuse.com/declarative-shadow-dom). Firefox 123 shipped 2024-02-20, "which means declarative shadow DOM is now available across the three major browser engines"; caveats: it is an HTML parser feature and does not work through `innerHTML` (use `setHTMLUnsafe`), and whitespace between the template and light DOM can be slotted (https://mayank.co/blog/declarative-shadow-dom-guide/). web.dev (Miller and Freed): the 2023 rename from `shadowroot` to `shadowrootmode` and the final semantics landed in Chrome 124; the parser attaches the root "immediately when their opening `<template>` tag is encountered" and "Parsed HTML within the `<template>` is parsed directly into the shadow root, so it can be 'streamed'"; calling `attachShadow()` on an element that already has a declarative root "will not throw an error. Instead, the Declarative Shadow Root is emptied and returned"; `ElementInternals.shadowRoot` exposes an existing open or closed declarative root, and the recommended constructor pattern is to check it and only then call `attachShadow()`; "if the same style sheet is present in multiple Declarative Shadow Roots, it is only loaded and parsed once. The browser uses a single backing CSSStyleSheet"; feature detection is `HTMLTemplateElement.prototype.hasOwnProperty('shadowRootMode')`, and a FOUC guard for non-supporting browsers is `:not(:defined) > template[shadowrootmode] { display: block }` (https://web.dev/articles/declarative-shadow-dom). MDN: only the first `<template shadowrootmode>` in a parent becomes a root, later ones stay templates, and "A HTMLTemplateElement cannot subsequently be changed into a shadow root after parsing"; sibling attributes `shadowrootclonable`, `shadowrootdelegatesfocus`, `shadowrootserializable`, `shadowrootslotassignment`, `shadowrootcustomelementregistry` and `shadowrootreferencetarget` exist (https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/template). For a static site on GitHub Pages there is no server streaming, but progressive parsing still means each pre-rendered chart paints as its bytes arrive, before any wasm.
19. What web-sys 0.3.104 gives us (local registry source; docs.rs dates the release 2026-08-08): `Element::shadow_root() -> Option<ShadowRoot>`, `Element::attach_shadow`, `Element::get_bounding_client_rect`; `ShadowRoot::{mode, host, inner_html, set_inner_html, adopted_style_sheets}`; `HtmlTemplateElement::content` only, no `shadow_root_mode`; no `gen_ElementInternals.rs` at all, which is why the site already reaches ElementInternals through `Reflect` and why closed declarative roots would need the same route; `ResizeObserver::{new, observe, disconnect}` with `ResizeObserverEntry`; `FontFaceSet::{ready, check, load}`; `OffscreenCanvas` and `OffscreenCanvasRenderingContext2d::measure_text`; `CanvasRenderingContext2d::measure_text(&self, text: &str) -> Result<TextMetrics, JsValue>` and `set_font(&self, value: &str)` behind the `CanvasRenderingContext2d` feature; `TextMetrics::{width, font_bounding_box_ascent, actual_bounding_box_ascent}`; `SvgTextContentElement::get_computed_text_length() -> f32`; `SvgGraphicsElement::{get_b_box -> Result<SvgRect, JsValue>, get_ctm, get_screen_ctm -> Option<SvgMatrix>}`; `SvgsvgElement::create_svg_point`; `Window::{request_animation_frame, match_media}` (https://docs.rs/web-sys/latest/web_sys/struct.CanvasRenderingContext2d.html).
20. What is cheap to animate. Chrome's blog: hardware-accelerated properties are `opacity`, `filter` and `transform`; "As of Chromium 89, Chrome will join the likes of Firefox to enable hardware-acceleration by default on SVG animations", shown by a spinner that repainted every frame in Chromium 88 and not in 89 or Firefox (https://developer.chrome.com/blog/hardware-accelerated-animations). Chromium commit 28a46da (2024-07-26, Philip Rogers) is "the first patch in a series of patches to optimize SVG transform updates", avoiding paint invalidation "when transforms change on elements with clip-path", worth 8.2% on MotionMark suites (https://github.com/chromium/chromium/commit/28a46da0087ff59fdf573b5674685fb6234d9b91). Motion's guide: CSS and Web Animations "drive animations like opacity and transform off-thread via the GPU"; SMIL cannot; "the majority of SVG animations like path drawing and morphing are still paint triggering. The thing that scales a paint is surface area ... it's always cheaper to animate transform instead of values like x, cx and r"; SVG 2 promoted `cx`, `cy`, `r`, `rx`, `ry`, `x`, `y`, `width`, `height` to CSS properties between 2020 and 2024; and rotation needs `transform-box: fill-box` because SVG transforms otherwise pivot on the viewBox origin (https://motion.dev/docs/svg-animation).
21. requestAnimationFrame: the callback runs "before the next repaint" at the display rate (60, 75, 120 or 144 Hz), is one-shot, receives a `DOMHighResTimeStamp` equal to the end of the previous frame that is shared by all callbacks in the same frame, is paused in background tabs and hidden iframes, and "some browsers have a multi-frame delay between the initial call to requestAnimationFrame() and the first call to the callback function" (https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame). Our clock ticks should therefore be coalesced: store the latest time, schedule one frame, apply once.

### Question 4: Text and layout

22. Measurement options compared. (a) Canvas `measureText` returns a `TextMetrics` (`width`, `actualBoundingBoxAscent`, `actualBoundingBoxDescent`, no height) and has been available since July 2015 (https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/measureText); on a 1 by 1 `OffscreenCanvas` it needs no DOM insertion and no layout, but it is single-line only, cannot give glyph positions, mishandles shaped scripts, and "Font must be loaded before measurement (use `document.fonts.ready` or `FontFace.load()`)" or it silently measures the fallback font (https://happyin.space/web-frontend/dom-free-text-layout/). (b) SVG `getComputedTextLength()` (since July 2015) returns the advance width of a live `<text>` (https://developer.mozilla.org/en-US/docs/Web/API/SVGTextContentElement/getComputedTextLength), and with `getBBox()` gives tight bounds, but "forces a synchronous layout, so reading it in a loop interleaved with writes is a textbook cause of layout thrashing"; the IDV guide's rule is set the font, measure everything in one read phase, decide, then write, and cache widths by font plus string (https://www.interactive-data-visualization.com/core-rendering-engines-tradeoffs/text-and-label-rendering/). (c) A glyph advance table: LogicAI measured `getBoundingClientRect` at roughly 8 to 15 thousand measurements per second, canvas `measureText` at "~200,000-400,000 measurements per second", and a per-character lookup table (224 characters measured once per font and size) at "2-4 million measurements per second"; the table ignores kerning pairs (GPOS or kern data would be needed), covers Latin only, and must be built after the font loads (https://logicaistudio.com/ai-strategy/pure-typescript-text-measurement-no-dom-reflow/). For us, ttf-parser can build the same table at build time from the site's actual font files, giving deterministic widths in wasm with no browser call. (d) `textLength` (since July 2015) makes the user agent "ensure that the text does not extend farther than that distance" by adjusting letter spacing (or glyph size with `lengthAdjust`), so "your SVG text displays at the same width regardless of conditions including web fonts failing to load" (https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/textLength); it stretches short labels too, so it is a guard for overflow cases, not a default.
23. Units and viewBox. SVG 2 section 8.4: "one unit in the initial coordinate system must equal one CSS 2.1 px", a unitless length on the outermost svg "is assumed to be equivalent to the same number of 'px' units", and (8.6) "The presence of the 'viewBox' attribute results in a transformation being applied to the viewport coordinate system" (https://www.w3.org/TR/SVG2/coords.html). MDN: with a viewBox "a transform stretches or resizes the SVG viewport to fit a particular container element", so `r="4"` renders at very different sizes under `viewBox="0 0 100 100"` and `"0 0 10 10"` (https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/viewBox); `font-size` on SVG text is a presentation attribute whose CSS counterpart wins and whose values are the CSS `font-size` values (https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/font-size). Consequence: whether a label is `font-size: 12px` or `0.75em`, it resolves to user units and scales with the viewBox stretch, so token-sized text is only guaranteed when the viewBox equals the rendered box.
24. Label placement algorithms. D3-Labeler (Evan Wang) runs simulated annealing over labels (`x`, `y`, `width`, `height`) and anchors (`x`, `y`, `r`), rejecting moves that cross the figure boundary, with a default of 1,000 sweeps (one sweep translates or rotates each label once on average), a linear cooling schedule, and an energy that penalises label-label overlaps, label-anchor overlaps, distance from the anchor, leader-line intersections and poor orientation; widths come from `getBBox()` (https://github.com/tinker10/D3-Labeler). d3fc-label-layout offers three strategies over rectangles `{hidden, x, y, width, height}`: greedy, which "adds each label in sequence, selecting the position where the label has the lowest overlap with already added rectangles and is inside the container"; annealing with `temperature` and `cooling` (iterations equal `ceil(temperature / cooling)`, output varies run to run); and remove-overlaps, which "removes overlapping labels ... iteratively, with the labels that have the greatest area of overlap removed first" and can wrap another strategy (https://github.com/d3fc/d3fc/blob/master/packages/d3fc-label-layout/README.md). For axis ticks the IDV guide's greedy left-to-right thinning (keep a label only if its left edge clears the previous kept label's right edge plus a gap) is enough (https://www.interactive-data-visualization.com/core-rendering-engines-tradeoffs/text-and-label-rendering/).

## Recommendations for the opt-chart renderer

1. Emission: a pure Rust writer with no runtime crates. One `<path d="M x y L x y ...">` per series with one-decimal coordinates (a `<polyline>` would also be one node, but a path lets the same emitter draw gaps for missing samples), grouped as `g.op-chart__grid`, `__axes`, `__series`, `__marks`, `__band`, `__chapters`, `__playhead`, `__labels`, each series carrying `op-chart__series--n` and a `data-series` attribute. No colour literals anywhere; every paint comes from a class rule that reads a token. Ids only where SVG needs them (`<clipPath>`), prefixed with a per-instance counter (`c3-plot`) because cross-tree `url(#id)` resolution is unspecified. `part="svg"`, `part="playhead"`, `part="series"` for outside theming through `::part`. When a series has more points than pixel columns, decimate to the minimum and maximum per column before emitting.
2. Coordinates: lay out in CSS pixels. Observe the host with ResizeObserver, set `viewBox="0 0 W H"` to the observed box, and re-run layout (ticks, label thinning, path strings) on resize, coalesced into one rAF; never rely on viewBox stretching, since px and em text would scale with it. Add `vector-effect: non-scaling-stroke` on all strokes as insurance for print scaling and zoom, `shape-rendering: crispEdges` only on axis-aligned grid lines, and `paint-order: stroke fill` with a background-coloured stroke on labels that cross lines.
3. Per tick, in concrete terms: at hydrate, cache handles to the playhead `<g>`, its `<text>`, and the played `<rect>`. On each clock event, store the time and, if no frame is pending, call `request_animation_frame` once. In the frame: compute x from the cached scale; if `|x - last_x| < 0.5` and the label is unchanged, return; else `set_attribute("transform", "translate(x 0)")` on the group, `set_text_content` on the label, `set_attribute("width", ...)` on the rect. Never touch the series paths, grid or axes on a tick. Skip frames while `document.hidden`. If the motion tokens allow easing, put a CSS `transition` on the group's `transform` (composited in Chromium 89+ and Firefox) and disable it under `prefers-reduced-motion`; do not animate `x1`/`x2` or `d`, which repaint.
4. Theming and modes: keep the token-to-class map in the shadow stylesheet. Add a `@media (forced-colors: active)` block with system colours only: text and axes `CanvasText`, series strokes `CanvasText` distinguished by `stroke-dasharray` and mark shape, band and played bar `Highlight` with `HighlightText` labels, background `Canvas`, gridlines `CanvasText` at reduced opacity (opacity is not a colour and is not forced). Give every series a dash pattern and a mark shape in all modes (WCAG 1.4.1) and strokes of 2 px or more (1.4.11 thin-line caveat). Under `prefers-contrast: more`, thicken strokes and make gridlines solid. Under `@media print`, set `print-color-adjust: exact` on filled bands and hide the playhead.
5. Text: at build time, read the site's font files with ttf-parser and emit a `const` advance table per weight (Latin plus the punctuation we use); estimate label widths from it in wasm; if `FontFaceSet::check` reports the font missing, fall back to `measure_text` on an `OffscreenCanvas` after `fonts.ready` and re-layout once; apply `textLength` only to labels whose estimate exceeds their slot. Ticks: port d3-ticks (about 60 lines) now; evaluate axis-labels Extended if wasm growth stays under about 2 KB. Labels: greedy candidate placement (eight positions around each anchor) followed by remove-overlaps, with no randomness so snapshots are stable; annealing is unnecessary at our mark counts.
6. Pre-render: have op-pages emit `<opt-chart for="..."><template shadowrootmode="open">` containing the classed SVG, a `<style>` with the shared class rules (deduplicated by the browser across charts), and a data hash attribute. On upgrade, the element calls `shadow_root()`; if a root exists and the hash matches, it caches handles and attaches listeners without re-rendering; if the hash differs or there is no root, it renders. Never call `attach_shadow` first, since that empties the declarative root. Do not use `<foreignObject>` for labels; the UA rule `svg|foreignObject { forced-color-adjust: auto }` would force its colours differently from the rest of the chart, and plain `<text>` is measurable and accessible.
7. Size: budget 20 KB of wasm for the renderer and measure every change with twiggy; use fixed-precision formatting and a single `String` builder; take kurbo only for op-webc machine edges (`fit_to_bezpath`, `offset`, arcs) behind a feature, after measuring; no Vello, plotters, charming or charts-rs.
8. Tests: insta snapshots of the emitted SVG for representative data (empty, one point, gaps, many points beyond the pixel width); resvg pixel tests per theme with the token stylesheet resolved to literal colours, both light and dark, checked against reference PNGs in CI; CDP real-render checks that drive the actual clock element and screenshot the chart under `setEmulatedMedia` for `prefers-color-scheme: dark`, `forced-colors: active`, `prefers-contrast: more` and `prefers-reduced-motion: reduce`, at `deviceScaleFactor: 2`; and a timing run of the tick path in Firefox on atlas (ppc64le, no wasm JIT) recording milliseconds per tick.

## Open questions for the other researchers

- Component API: with a declarative root the chart exists before the wasm upgrades, so how does `for=` bind to a clock element that may itself not be defined yet, and where does the data live (attributes, a `<script type="application/json">` child, or slotted markup)? seek and peek intents need the plot rectangle and the time scale, which the renderer can export as attributes on the host.
- Accessibility: the role and naming of the SVG (a single `img` with `<title>` versus a graphics document with per-mark names); whether tick and grid text should be hidden from assistive technology behind a table alternative; the exact forced-colours palette (is `Highlight` right for the played band, and should chapter bars use `Mark`?); the dash and marker scheme per series; and whether the playhead value is announced, and how often.
- Timeline UX: eased versus stepped playhead motion and its reduced-motion form; hover and focus states for chapter bars and marks (each is a node, so cheap in SVG); expected series and point counts, which decide whether decimation ever triggers; and which pointer gestures on the plot mean peek versus seek.
