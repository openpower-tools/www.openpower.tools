# Chart web components 2024 to 2026: what exists and what opt-chart should copy

Facet 1 of 4: how charts are built as web components, and the component API patterns worth adopting. Every source was fetched and read on 2026-09-03; nothing is cited from memory. Two planned pages could not be crawled (Carbon's Storybook "tabular data format" page and Vaadin's "Usage with Lit" page); the package READMEs were used instead and this is noted where it matters.

## Summary

- No mainstream chart library ships a first-class custom element. The elements that do exist (google-chart, vaadin-chart, tanstack-chart, several sparkline elements, ECharts and Vega wrappers) converge on the same shape: rich data through a JavaScript property, primitives through attributes, one prefixed composed CustomEvent per user intent, a CSS custom property per series colour, and a ResizeObserver-driven re-render.
- The one production precedent for our "classed SVG, no colour literals" plan is Highcharts styled mode (also the engine under Vaadin Charts): no presentational attributes in the SVG, a class per series index and per element type, a CSS file with variables that follow prefers-color-scheme. Its stated limit is that geometry (x, y, width, height) cannot come from CSS.
- TanStack Charts (alpha 0.16, 2026) is the closest modern reference for the element contract: everything through an options object, `idPrefix` for renderer-owned SVG IDs, `initialWidth` plus `aspectRatio` for server output, a deterministic server text measurer with browser re-measurement after fonts load, stable keys, `currentColor` and `--ts-chart-*` tokens.
- Wiring: `for=` style ID references are the platform idiom (label for, popovertarget, commandfor, interestfor). Reference Target (Chrome 152) forwards such references into a shadow tree. The Context Community Protocol is for data flowing down a subtree and explicitly not a state manager, so it is the wrong tool for wiring a chart to a sibling film.
- Baseline status today: custom states and light-dark() (2024); popover, commandfor and same-document View Transitions (2025); anchor positioning (January 2026) and contrast-color() (April 2026). Not Baseline: scroll-driven animations, container style queries (partial in Chrome and Safari), interestfor (Chrome 142 only), Reference Target (Chrome 152 only).
- SVG in shadow DOM: fragment references (`use href="#id"`, `url(#id)` for gradients, clip paths, markers, filters) resolve inside the shadow tree in all engines after WebKit's 2018 and June 2023 fixes, so each shadow root is a free ID namespace; references from inside a shadow root out to the light DOM do not work in any engine.
- Declarative Shadow DOM gives build-time SVG with a no-JS fallback; a component must check `internals.shadowRoot` in its constructor and never call `attachShadow` blindly, because that empties the declarative root.
- Recommendation in one line: a `<script type="application/json">` data block plus a `data` property, DSD-prerendered classed SVG, `--op-series-N` tokens under the existing contrast test with matching parts, `opt-chart-seek` and `opt-chart-peek` events, custom states mirrored from the film, ResizeObserver re-render in wasm, and build-time text metrics via rustybuzz against the served font.

## Findings

### A. Existing chart elements and their API shapes (question 1)

1. google-chart (Google Web Components, Lit since v4). The README shows the whole declarative surface: `<google-chart data='[["Month", "Days"], ["Jan", 31]]'></google-chart>`, with the note that JSON in attributes needs single quotes and that "Height and width are specified as style attributes". The v4 migration removed the Polymer-generated `selection-changed` event, keeping only `google-chart-select` "for consistency with other events (e.g. google-chart-ready)", and removed the `google-chart-loader` element in favour of `dataTable` and `load` exports from `loader.js`. The TypeScript source (google-chart.ts) details the contract:
   - `type` is a reflected string attribute (default `column`) mapped to Google constructor names (`area`, `bar`, `md-bar`, `bubble`, `calendar`, `candlestick`, `column`, `combo`, `gantt`, `gauge`, `geo`, `histogram`, `line`, `md-line`, `org`, `pie`, `sankey`, `scatter`, `md-scatter`, `stepped-area`, `table`, `timeline`, `treemap`, `wordtree`).
   - Data can arrive four ways: `cols` plus `rows` arrays; `data` as a two-dimensional array or DataTable object; `data` as a URL string (the element `fetch()`es JSON); or `view` as a DataView. `data` is declared `type: String` because "it is parsed manually in the observer": it tries `JSON.parse`, treats a failure as a URL if the value is a string, and otherwise uses the object as is.
   - `options` is an object property with `hasChanged: () => true` so every assignment redraws; mutating a sub-property requires reassigning the object ("Missing parent properties are not automatically created").
   - `events` lists extra Google chart events to propagate; "Changes to this property are not observed. Events are attached only at chart construction time." `ready` and `select` always propagate.
   - `selection` is a read/write array of `{row, column}`; the element calls `chart.setSelection` when set and updates the property when the chart fires `select`, with a special case because the timeline chart "emits select event on setSelection" (issue #256).
   - Every propagated event is re-dispatched as `google-chart-<name>` with `bubbles: true, composed: true, detail: { chart, data }`.
   - `redraw()` is public and debounced by a 5 ms timeout; its doc says "Call manually to handle view updates, page resizes, etc.", so the element has no ResizeObserver. `drawn` and an `imageURI` getter are exposed.
   - Styles: `:host { display: flex; width: 400px; height: 300px }`, `:host([hidden]) { display: none }`, `:host([type="gauge"]) { width: 300px; height: 300px }`. A `localizeGlobalStylesheets()` step clones Google's `link#load-css-*` stylesheets from `document.head` into a `div#styles` in the shadow root "for shadow dom support", which is what shadow DOM costs when the renderer expects global CSS.
   Sources: https://github.com/GoogleWebComponents/google-chart and https://raw.githubusercontent.com/GoogleWebComponents/google-chart/main/google-chart.ts (2026-09-03).

2. Vaadin Charts (`@vaadin/charts`, commercial, Highcharts underneath). The README's entire example is declarative light-DOM children: `<vaadin-chart type="pie"><vaadin-chart-series values='[["Firefox", 45.0], ["IE", 26.8], ["Chrome", 12.8], ["Safari", 8.5], ["Opera", 6.2], ["Others", 0.7]]'></vaadin-chart-series></vaadin-chart>`. The styling page describes two tiers and a rule: "CSS and the Java Styling API can't be used in the same chart". Built-in theme variants are `gradient`, `monotone` and `classic` (Lumo). The public CSS tier is custom properties settable "in any regular application stylesheet", for example `vaadin-chart.first-chart { --vaadin-charts-color-0: green; --vaadin-charts-color-1: lightgreen; --vaadin-charts-color-2: darkgreen; --vaadin-charts-data-label: red; }`. The deep tier is Highcharts class names, which "requires the styles to be injected into the chart's shadow DOM" through a `vaadin-chart.css` file in the theme's components folder, "disabled by default" behind the `themeComponentStyles` feature flag, for example `:host(.first-chart) .highcharts-color-0 .highcharts-point { fill: yellow; stroke: purple; stroke-width: 2px; }`; individual elements can be given class names (`setClassName("bold-green-axis")`) and styled with `.bold-green-axis { font-weight: bold; fill: green; font-size: 14px; }`. Flow applications default to the Java styling API and switch to CSS with `setStyledMode(true)`. The basic-use page (Java API) shows the data model: a `Configuration` holding `ListSeries`/`DataSeries` objects with names, `XAxis` categories, label formatters as JavaScript strings, and per-series plot options that allow mixed chart types. Sources: https://github.com/vaadin/web-components/blob/main/packages/charts/README.md , https://vaadin.com/docs/latest/components/charts/styling , https://vaadin.com/docs/latest/components/charts/basic-use (2026-09-03). The Lit usage page returned 404 (CRAWL_NOT_FOUND).

3. Highcharts styled mode (the engine behind Vaadin's CSS tier). With `chart.styledMode` true, "no presentational attributes (like fill, stroke, font styles etc.) are applied to the chart SVG. Instead, the design is applied purely by CSS." A default `css/highcharts.css` ships; since v11 it "honors the prefers-color-scheme CSS media feature" and a `.highcharts-light` or `.highcharts-dark` class on the container pins a scheme. The limit is explicit: "layout and positioning of elements like the title or legend cannot be controlled by CSS. This is a limitation of CSS for SVG, that does not (yet - SVG 2 Geometric Style Properties) allow geometric attributes like x, y, width or height. And even if those were settable, we would still need to compute the layout flow in JavaScript." The class taxonomy: `.highcharts-root` (inherited typography), `.highcharts-series` and `.highcharts-{type}-series` and `.highcharts-series-{n}` (index-based series classes) plus a `className` option, `.highcharts-graph` (replaces `color`, `lineWidth`, `dashStyle` options), `.highcharts-background`, `.highcharts-axis` with `.highcharts-xaxis`/`.highcharts-yaxis`/`.highcharts-coloraxis`, `.highcharts-plot-border`, `.highcharts-plot-background`, `.highcharts-plot-line` and `.highcharts-plot-line-label` (our marks), `.highcharts-selection-marker`. Source: https://www.highcharts.com/docs/chart-design-and-style/style-by-css (2026-09-03).

4. IBM Carbon Charts. The main README calls it "A component library of 26 charts for vanilla JavaScript, Svelte, React, Vue.js and Angular", implemented with D3 and TypeScript; the core README says styles must be imported from `@carbon/charts/dist/styles.css` and notes IBM Telemetry collection. It is not a custom element library; there is no web components package. The Svelte README (used because the Storybook data-format page failed to crawl) shows the data and options contract: `data={[{ group: 'Qty', value: 65000 }, { group: 'More', value: 29123 }, ...]}` (tidy long-format rows) and `options={{ theme: 'g90', title: 'Simple bar (discrete)', height: '400px', axes: { left: { mapsTo: 'value' }, bottom: { mapsTo: 'group', scaleType: 'labels' } } }}`. Lifecycle callbacks are `onload`, `onupdate`, `ondestroy`; interaction events are subscribed on the chart instance, `chart.services.events.addEventListener('bar-mouseover', fn)`. SSR is unsupported: the README recommends dynamic import in `onMount` because `@carbon/charts` "expects the window object to be present for fullscreen display". Sources: https://github.com/carbon-design-system/carbon-charts , https://github.com/carbon-design-system/carbon-charts/blob/main/packages/core/README.md , https://github.com/carbon-design-system/carbon-charts/blob/main/packages/svelte/README.md (2026-09-03).

5. Adobe React Spectrum Charts. React only, on Vega and Vega-Lite as peer dependencies (`npm install @adobe/react-spectrum-charts @adobe/react-spectrum vega vega-lite`). The API is composition by children: `<Chart data={myChartData}><Axis position="bottom" /><Axis position="left" /><Bar type="stacked" color="series" /><Legend /></Chart>`, described as "The code reads just like you would explain the chart to someone else." A Spectrum 2 alpha package adds line gradients, direct labels and reference lines; the latest release is v1.45.0 (2026-06-10); 30+ date and number locales. Source: https://github.com/adobe/react-spectrum-charts (2026-09-03).

6. Salesforce Lightning Web Components. The developer guide's answer to charts is third-party libraries: "use a library with interactive charts and graphs". The D3 recipe uploads the library as a static resource, calls `loadScript` and `loadStyle` from `lightning/platformResourceLoader` in `renderedCallback()` with `Promise.all`, renders into `<svg class="d3" lwc:dom="manual">` because "The lwc:dom="manual" directive tells LWC that the DOM in the svg element has been inserted manually", and queries with `this.template.querySelector` because "you can't use document to query for DOM elements" (DOM access containment). The lwc-recipes Chart.js variant uses an initialisation guard flag, creates the canvas programmatically and sets `responsive: false`. Salesforce Labs' LightningWebChartJS (Chart.js underneath) is the nearest thing to a chart component: `<c-chart type="bar"><c-title text="# of LWCC installs"></c-title><c-legend position="bottom"></c-legend></c-chart>`, with an App Builder property sheet (type picklist, title, legend position, CSS style, palette picklist including `colorsafe`, fill flag, dataset labels as a JSON array, dataset as a JSON array of `{labels, detail}` objects, a SOQL string with `label` and `value` aliases, or a custom Apex data provider). Sources: https://developer.salesforce.com/docs/component-library/documentation/en/lwc/js_third_party_library , https://salesforcelabs.github.io/LightningWebChartJS/ , https://trailheadapps-lwc-recipes-82.mintlify.app/components/libs/chartjs (2026-09-03).

7. TanStack Charts (alpha, latest release 0.16.0, docs follow unreleased `main`). It is "a small, framework-agnostic chart grammar for TypeScript and JavaScript" in the grammar-of-graphics line (Wilkinson, ggplot2, Vega-Lite, Observable Plot) that "renders accessible SVG by default, with Canvas available as an opt-in surface", and is designed for two authors, people and AI agents. It owns "Container-responsive pixel ranges and automatic guide margins", "A renderer-neutral scene with stable keys", keyed DOM reconciliation, interruptible animation, pointer and keyboard focus, tooltips, and "Light and dark mode defaults based on inherited color and CSS variables"; the defaults are "Omit width to follow the chart container", "Omit margin to measure axes, tick labels, rotation, and titles automatically", "Supply ariaLabel; keyboard focus is enabled by default", and "Use inherited currentColor and the --ts-chart-* CSS variables for automatic theme integration".
   - Lit element: `import { Chart, defineChartElement } from '@tanstack/charts/lit'`; `defineChartElement(tagName = 'tanstack-chart')` is idempotent. "Pass the complete chart value through the element's options property, not HTML attributes. Replace the definition identity when captured application values change." Options: `definition` (required), `ariaLabel` (required), `ariaDescription`, `height` (320 without a ratio), `aspectRatio`, `width` (fixed, else responsive), `initialWidth` (640), `tabIndex` (0; `keyboard: false` forces -1), `idPrefix` (generated; "Prefix for renderer-owned document IDs"), `renderSvg`, `measureText` (`ChartTextMeasurer`), `onFocusChange(point | null)`, `onFocusGroupChange(points)`, `onSelect(point | null)` for pointer or keyboard activation, `onRender(context)`, `renderTooltipBody({ points, defaultBody, pinned, dismiss })` composing Lit templates inside the built-in tooltip, plus `class`, `style`, `className`.
   - SSR guide: the adapter table lists Lit as "Not yet a verified adapter contract" for hydration (browser registration, update, disconnect, reconnect only). "The server cannot measure a container", so one of four size policies is required: `width` and `height`; `width` and `aspectRatio`; `initialWidth` and `height`; `initialWidth` and `aspectRatio`. Determinism rules: module-scope definitions, sort unordered collections, "do not read window, layout, time, locale, or random values while building a definition", pass locale-sensitive formatters explicitly, supply explicit keys when data has no stable identity, and "provide idPrefix when multiple render roots need coordinated resource IDs". Fonts: "The server uses deterministic fallback measurement unless you provide measureText. The browser host remeasures when fonts become available and schedules a new layout." `ChartTextMeasurer` is synchronous and receives family, style, stretch, letter spacing, direction, locale and font scale; strict pixel parity needs the same font, a deterministic measurer and the same typography on both sides, but "Most applications should allow the browser's post-font layout correction instead of shipping a font engine to the server." Without a framework, `createChartRuntime().render(definition, { width, height })` then `renderChartSvg(scene, { ariaLabel, idPrefix })` "returns a string and does not require a DOM".
   Sources: https://tanstack.com/charts/latest/docs/framework/lit/overview , https://tanstack.com/charts/latest/docs/framework/lit/reference/chart.md , https://tanstack.com/charts/latest/docs/guides/ssr-and-hydration (2026-09-03).

8. Sparkline custom elements. Four were read; they show the range of intake and theming styles at the small end.
   - `<svg-sparkline values="8,3,2,7,9,1,5,6,4,10,3,8,2,7,1,9">` (Chris Burnell) builds SVG in its shadow root. Attributes: `values` (required, comma-separated), `width` (200), `height` (36), `color` (`currentColor`), `curve`, `endpoint` (true), `endpoint-color`, `endpoint-width` (6), `fill`, `gradient`, `gradient-color`/`fill-color`, `line-width` (2), `start-label`, `end-label`, `animation-duration` (1s), `animation-delay`. Site-wide overrides are CSS variables on `:root`: `--svg-sparkline-color`, `--svg-sparkline-endpoint-color`, `--svg-sparkline-gradient-color`, `--svg-sparkline-padding`, and animation duration and delay variables. The page states plainly that "this Web Component requires JavaScript to function correctly".
   - `<spark-line values="[0,30,35,45,65,100,85,100]" fill showlast>` (Eric Bidelman) deliberately has no shadow DOM ("styles are scoped in sass"); the consumer gives it layout with `spark-line { display: inline-block; width: 100%; height: 75px; contain: content; }`; it shows data points on hover and colours by Lighthouse score thresholds.
   - sparklines.js exposes `<spark-line>`, `<spark-bar>`, `<spark-tristate>`, `<spark-discrete>`, `<spark-bullet>`, `<spark-pie>`, `<spark-box>`: `values` as a comma list attribute or an array property, `options` as a property for complex options, "Attribute names use kebab-case and map to option keys (e.g. line-color -> lineColor)", and "Re-renders when attributes or the values/options properties change". Rendering is canvas.
   - rms-sparkline-inline (canvas): "The web element does not offer an API. Its interactions are controlled by changing its attributes", with the Angular-binding caveat that attribute names are all lowercase while the bound properties are camel-cased.
   Sources: https://chrisburnell.com/svg-sparkline/ , https://github.com/chrisburnell/svg-sparkline , https://github.com/ebidel/spark-line/ , https://github.com/maxkostinevich/sparklines.js/ , https://registry.npmjs.org/rms-sparkline-inline (2026-09-03).

9. ECharts wrappers. lit-echarts exposes properties `theme`, `option` (the full ECharts option, set as `dom.option = option`), `replaceMerge`, `noMerge`, `showLoading`, `loadingOption`, `opts` (init options such as renderer), `onEvents` (`{ eventName: handler }`), `onChartReady`, `noData`; it watches its own size with size-sensor ("No need to handle resize outside of component") and compares options with fast-deep-equal. echarts-web-components defines per-type elements (`<e-line-chart>`) driven by `dimensions`, `source`, `chartTitle`, `yName` properties that re-render on assignment. A 2024 Lit tutorial shows the canonical lifecycle: `@property({ type: Array }) value`, build options in `willUpdate`, `init()` the engine in `firstUpdated` and attach `new ResizeObserver(() => instance.resize())`, call `setOption` in `updated`, disconnect the observer and `dispose()` in `disconnectedCallback`, and register only the needed chart and component modules for bundle size. vue-echarts (Vue, not a custom element, but the most used wrapper) takes one `option` prop, computes an update plan (removed objects become `null`, removed arrays become `[]` with `replaceMerge`, risky changes fall back to `notMerge: true`), re-exposes ECharts events, and requires a `native:` prefix to bind real DOM events, a reminder that wrapper events are not DOM events. Sources: https://github.com/cherie-xf/lit-echarts , https://github.com/jackchoumine/echarts-web-components , https://dev.to/manufac/using-apache-echarts-with-lit-and-typescript-1597 , https://github.com/ecomfe/vue-echarts (2026-09-03).

10. Vega. Vega-Embed itself is a function, `embed(el, spec, opt)`, where `spec` is "A URL string from which to load the Vega specification" or "the Vega/Vega-Lite specification as a parsed JSON object"; `mode` is inferred from `$schema`; it returns `{ view, spec, vgSpec, finalize }` and `finalize()` must be called to unregister timers and listeners; the Vega-Lite site's recommended embedding is a `<div id="vis">` plus `vegaEmbed('#vis', yourVlSpec)`. Two custom-element wrappers exist: PolymerVis `<vega-embed spec="/path/to/some/vega/spec.json">` (lit-element based; `spec` also settable as an object property, attributes such as `show-export`, properties such as `showSource`, an `opts` property), and a 2023 HTMX-oriented `<vegalite-plot>` that "takes the plot spec as its text content", watches it with a MutationObserver, and serialises asynchronous re-renders with two counters (`_specUpdate`, `_domUpdate`) so an older render can never overwrite a newer one. Sources: https://github.com/vega/vega-embed , https://vega.github.io/vega-lite/usage/embed.html , https://github.com/PolymerVis/vega-element/ , https://cprohm.de/blog/vega-with-htmx/ (2026-09-03).

11. Plotly. The only Plotly custom element found is `plotly-plot` (Ginkgo Bioworks, Polymer, 2016, v0.5.0): `data`, `layout`, `config` properties trigger redraws, the update methods `redraw`, `restyle`, `relayout`, `addTraces`, `deleteTraces`, `moveTraces` are exposed, and Plotly events are replicated. Its README recommends wrapping it in your own element with a narrower API (a `my-pie-chart` with `values`, `labels`, `title`). The icon toolbar layout code in the plotly.js library fails for all plotly plots rendered inside a shadow DOM, whether by Polymer or any other means." That claim is from 2016 and I did not verify it against current plotly.js; `angular-plotly.js` uses the same `<plotly-plot>` tag name but is an Angular component. Sources: https://github.com/ginkgobioworks/plotly-plot/ , https://www.npmjs.com/package/plotly-plot , https://github.com/plotly/angular-plotly.js (2026-09-03).

12. Timeline and scrubber elements. No maintained chart-adjacent timeline custom element was found beyond commercial Smart UI `<smart-timeline>` (configured by a properties object via `Smart('#timeline', class { get properties() {...} })`, `change` events with `event.detail`) and the `timeline` chart type inside google-chart. The interesting scrubbers are framework components: immich's Svelte `Scrubber` (props `onScrub`, `startScrub`, `stopScrub`, `onScrubKeyDown`; Tab handled explicitly to hop to the next tabbable element, ArrowUp/ArrowDown move by month segment, touch resolved with `document.elementsFromPoint`); VLLNT's React `TimelineScrubber` (built on a native `input type=range` "so keyboard, pointer, and screen-reader support come for free"; props `start`, `end`, `value`, `step`, `ticks` with `id`, `label`, `tone`, `value`, `onValueChange`, `formatValue`; "The host owns the value and drives the playback loop; the component is pure presentation"); svelte-p5's `TimelineTrack` (click-to-seek, drag playhead, view window, segment bands, `onHover` plus a `hoverIndicator` snippet, CSS custom properties) with `createMediaSync`, which locks the timeline to `mediaTime` while media plays and writes back with a clamped `seek(time)`; and omakase-player's canvas scrubber lane (Konva, RxJS `onClick$`/`onMouseMove$` observables, tick spacing chosen by a minimum division width). These belong to the timeline researcher; they are listed so the API vocabulary (seek, scrub start/stop, ticks, host owns value) is shared. 13. Sizing patterns. Three approaches appear.
   - Re-render on resize: `<neiki-chart>` (zero-dependency SVG element) does "ResizeObserver-driven redraws fill any container automatically", with `width`/`height` attributes only for explicit pixel sizes ("Omit to fill container"), `theme` (`light`, `dark`, `auto` following prefers-color-scheme), `legend`, `tooltip`, `animated`, `grid`, `colors` (a comma-separated list of CSS colours), per-type `smooth`, `area`, `orientation`, `inner-radius`; tokens `--nc-bg`, `--nc-text`, `--nc-grid`, `--nc-tooltip-bg` overridable from outside the shadow root; `role="img"` and `aria-label` on the chart; if ResizeObserver is missing it "renders once on connect and does not auto-resize". The d3-lit-dashboard `<line-chart>` takes `width`, `height`, `xAxisLabel`, `yAxisLabel`, `scaleType`, `strokeWidth`, `pointRadius`, `smoothCurve`, `theme` attributes and exposes `--bg-color`, `--axis-color`, `--axis-text-color`, `--tooltip-bg-color`, `--tooltip-text-color`, `--tooltip-radius`. lit-echarts and the Lit tutorial in finding 9 call the engine's `resize()` from a ResizeObserver. TanStack follows the container when `width` is omitted and renders at `initialWidth` first.
   - viewBox scaling with separated text: Build UI's server-rendered line chart keeps text at CSS size by using three SVGs: an x-axis SVG and a y-axis SVG without `viewBox` (so `font-size: 14px` and `tabular-nums` apply as written, positioned with percentage coordinates), and a chart-area SVG containing a nested `viewBox="0 0 100 100" preserveAspectRatio="none"` SVG for grid lines, the line and the points, all with `vector-effect="non-scaling-stroke"`. Margins are CSS variables (`--marginTop: 6px`, `--marginLeft: 25px`) applied with `calc()`, and container queries (`@sm:`) swap short and long weekday labels; the author's argument is that percentage margins are "not enough space on a phone, and it's too much space on a large monitor".
   - Manual: google-chart's `redraw()`.
   MDN confirms `vector-effect: non-scaling-stroke` (Baseline since July 2020) makes "the stroke width ... not dependent on the transformations of the element (including non-uniform scaling and shear transformations) and zoom level", and that the three other values (`non-scaling-size`, `non-rotation`, `fixed-position`) "have no implementations and are considered at-risk". Lit's styling docs add the general rule behind all of these tokens: static `styles` are "evaluated once per class", so per-instance theming should go through CSS custom properties such as `:host { background-color: var(--my-background, yellow) }`.
   Sources: https://github.com/neikiri/neiki-charts , https://github.com/OrderAndCh4oS/d3-lit-dashboard , https://buildui.com/recipes/responsive-line-chart , https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/vector-effect , https://lit.dev/docs/components/styles/ (2026-09-03).

### B. Protocols and platform features for wiring elements (question 2)

14. Properties versus attributes. web.dev's checklist: create the shadow root in the constructor; put element-created children in the shadow root; use `<slot>` for author content; set a `:host` display (custom elements are `display: inline` by default so width and height "will have no effect"); add `:host([hidden]) { display: none }` because a `:host { display: block }` rule outranks the `hidden` attribute; "Do not override author-set, global attributes" (check `role` and `tabindex` before setting them); "Always accept primitive data (strings, numbers, booleans) as either attributes or properties" and keep them in sync, except high-frequency values ("You shouldn't reflect high frequency properties, e.g. currentTime in a video player"); "Aim to only accept rich data (objects, arrays) as properties" because serialising is expensive and object references are lost; "Do not reflect rich data properties to attributes"; check for properties set before upgrade with the `_upgradeProperty(prop)` pattern (`if (this.hasOwnProperty(prop)) { let value = this[prop]; delete this[prop]; this[prop] = value; }`); "Do not self-apply classes" (the class attribute belongs to the page author); "Dispatch events in response to internal component activity" and "Do not dispatch events in response to the host setting a property (downward data flow)" because it "may cause infinite loops with data binding systems"; and avoid reentrancy when reflecting inside `attributeChangedCallback`. open-wc adds that attributes are always strings, that boolean attributes are true when present regardless of value (`disabled="false"` is still disabled), and its rule of thumb: "Set properties when working with JS; set attributes when working with just HTML; sync attribute changes to the corresponding JS property; don't sync property changes to the corresponding HTML attribute" because "properties can update often and triggering a DOM change for each update can impact performance". Sources: https://web.dev/articles/custom-elements-best-practices , https://open-wc.org/guides/knowledge/attributes-and-properties/ (2026-09-03).

15. JSON data blocks. MDN: for `<script type>`, "Any other value" than a JavaScript MIME type, `importmap`, `module` or `speculationrules` means "The embedded content is treated as a data block, and won't be processed by the browser. 16. Context Community Protocol (WCCG, status Candidate, last update 2025-05-02). Goals: let elements "retrieve data based on their contextual position in the DOM", remove prop drilling, stay a "Simple API that is easily implemented in any framework / library", be synchronous while supporting asynchronous patterns, and support single or multiple delivery. Non-goals are explicit: "Context API !== Dependency Injection Framework" and "Context API is not a state management alternative". Mechanics: a consumer fires a composed, bubbling `context-request` event carrying `context` (the key, compared with strict equality, so a unique Symbol or object makes a private context and a string or `Symbol.for()` makes a shared one), `callback`, and optional `subscribe`; a provider that can satisfy it "MUST call stopImmediatePropagation" (preferably before invoking the callback, or in a try/catch, so a throwing callback cannot leave the event propagating), must invoke the callback immediately if data is available, may retain the callback and pass an `unsubscribe` function only when `subscribe` is truthy, and should hold subscriptions through WeakRefs; "A provider does not necessarily have to be a Custom Element". Lit implements the protocol in `@lit/context` with `createContext()`, `@provide({ context })` and `@consume({ context })` decorators (consumers paired with `@property({ attribute: false })`), and subscriptions; Lit's docs say it exists for "data that needs to be consumed by a wide variety and large number of components ... or when data-binding isn't an option, such as when an element needs to provide data to its light DOM children". Sources: https://github.com/webcomponents-cg/community-protocols/blob/main/proposals/context.md , https://lit.dev/docs/data/context/ (2026-09-03).

20. Declarative Shadow DOM. Supported in Chrome from 90, with the 2023 spec change renaming `shadowroot` to `shadowrootmode` and "the most up to date standardized versions of all parts of the feature" landing in Chrome 124. A `<template shadowrootmode="open">` inside a host is "detected by the HTML parser and immediately applied as the shadow root of its parent element", giving encapsulation and slot projection "in static HTML. No JavaScript is needed to produce the entire tree." The motivation is server or build-time rendering without layout shift or "a flash of unstyled content" from late `attachShadow`. For custom elements: calling `attachShadow()` on an element with a declarative root "will not throw an error. Instead, the Declarative Shadow Root is emptied and returned", so hydration code must check `internals.shadowRoot` (open or closed) in the constructor and only create a root when it is null; the article's pattern is `let shadow = internals?.shadowRoot; if (!shadow) { shadow = this.attachShadow({ mode: "open" }); shadow.innerHTML = ... }` then wire listeners in both cases. One shadow root per element, colocated, streamable; the design deliberately does not let several elements share one template. Parser-only: setting `shadowrootmode` from script does nothing and `innerHTML`/`insertAdjacentHTML` ignore it; only `setHTMLUnsafe()` or `parseHTMLUnsafe()` parse declarative roots after load. Source: https://web.dev/articles/declarative-shadow-dom (2026-09-03).

### C. SVG inside shadow DOM (question 3)

22. Fragment references resolve per tree scope, after a long fight. The 2015 WICG thread (#179) shows the dissent: rniwa argued that `href` on `<use>` "uses an URL and an URL has a very well defined semantics" and that overriding it inside shadow trees would be "an arbitrary inconsistency", proposing a new attribute instead; Amelia Bellamy-Royds laid out the consequences of shadow-local resolution (shadow-to-light references would need the full document URL and interact with `<base>`; `url(#effect)` in CSS can inherit from light into shadow; `<use>` element shadow trees need cloned references made absolute); Tab Atkins' position, which became the consensus, was that fragment identifiers should be "local to the shadow tree, like what HTML forms do" and that URLs should follow CSS Values rules where "fragment-only URLs are specially treated as always-local". The 2018 split-out issue (#772) records "The rough consensus at TPAC is that URLs in SVG href content attribute should use CSS's rules ... and thus act like fragment IDs and be scoped to the shadow tree", a frustrated user comment ("Don't use Shadow DOM until this is fixed in the spec and in all browsers"), a report that the pattern already worked in Chrome and Firefox but failed in Safari, and rniwa's follow-up: "This should be working on iOS 12.2 and macOS 10.14.4 betas now. Given all major browser engines support this, the only remaining work is to update the spec accordingly", adding "there doesn't seem to be much effort trying to update the standards". WebKit's first fix (bug 174977, opened 2017-08-01, changeset 238524) made `targetElementFromIRIString` take a `TreeScope` instead of a `Document` for `use`, `textPath`, `mpath`, `feImage`, gradient `href` chains and filters, and deleted the `FIXME: Enable SVG use elements in shadow trees` early return; its second fix (commit 9057e67, 2023-06-27, bug 212820, "SVG fragment reference fails in shadow tree under some circumstances") moved the SVG resource registry itself into `TreeScope` (`svgResourcesMap`, pending resources) because "SVG fragment references [were] looking up elements in the document tree instead of in each shadow tree", introduced `Node::treeScopeForSVGReferences` so references inside a `<use>` clone resolve in the tree where the `<use>` lives, touched clip-path, CSS filter and paint server lookups, and added tests named `svg-multiple-references-in-multiple-shadows-{linear-gradient, radial-gradient, rect}`. The SVG WG issue (#505) that reported "a square in Blink, and nothing in WebKit and Firefox" for a shadow-local `<use>` says "I haven't found spec text to back this up or define this in any reasonable way"; I did not find a merged spec resolution, so the guarantee rests on shipped engine behaviour and WebKit's layout tests rather than on spec text. The reverse direction is settled the other way: a Stack Overflow thread concludes that a `<use>` inside a shadow root referring to a light-DOM fragment "is consistently a no-go across FF/Chrome/Safari", with workarounds of appending the symbol SVG into the shadow root or keeping a global icon registry. MDN's `<use>` page adds the general cautions: attributes on `<use>` other than `x`, `y`, `width`, `height`, `href` are ignored when already set on the referenced element; "CSS properties are not guaranteed to be inherited by the cloned DOM unless you explicitly request them"; browsers may apply the same-origin policy to `href`; external-file references (`file.svg#id`) and, in modern engines, whole-file references without a fragment work; data URIs in `href` are deprecated. Sources: https://github.com/WICG/webcomponents/issues/179 , https://github.com/WICG/webcomponents/issues/772 , https://bugs.webkit.org/show_bug.cgi?id=174977 , https://trac.webkit.org/changeset/238524/webkit/ , https://github.com/WebKit/WebKit/commit/9057e67f74027a0a28d82230b35263cf724de030 , https://github.com/w3c/svgwg/issues/505 , https://stackoverflow.com/questions/62196618/svg-use-element-href-referring-to-element-outside-of-shadowroot , https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/use (2026-09-03).

23. ID collisions between charts on one page. Consequence of finding 22: two charts each rendering `<linearGradient id="band">` inside their own shadow roots do not collide, because lookups are per tree scope; WebKit's 2023 tests exercise exactly "multiple references in multiple shadows". Collisions remain possible in two situations: SVG emitted into the light DOM (documentation pages, or any chart rendered without a shadow root as `spark-line` does), and any `<use>` that tries to share a `<symbol>` across roots, which cannot work. TanStack's answer for the light-DOM case is a per-chart `idPrefix` for "renderer-owned document IDs", supplied "when multiple render roots need coordinated resource IDs", and its server renderer takes `idPrefix` as an option to `renderChartSvg`. Sources: findings 7 and 22.

24. Focus and keyboard on SVG. `tabindex` on any SVG element is Baseline Widely available "since January 2017" (SVG 2; not animatable). The SVG Accessibility API Mappings working draft of 2026-03-11 states that "SVG 2 now incorporates keyboard navigation based on the established model from HTML 5", that user agents must include in the accessibility tree any rendered element with a valid integer `tabindex`, a non-presentational ARIA role, text content, or current keyboard focus, "regardless of whether they would otherwise be considered hidden or presentational", and that `tabindex` on SVG is interpreted "as defined in the HTML Attribute State and Property Mappings". The historical caveats from ally.js (SVG 1.1 had no focus model, SVG Tiny 1.2 added `focusable`, Firefox lacked `.focus()` on SVG elements until 51, IE and old Edge used `focusable` instead of `tabindex`, the `outline` property was unsupported on SVG elements in older engines, `<a>` inside `<use>` and hidden SVGs stranded keyboard users in Safari 8 and 10) are mostly retired, but two of its rules still hold: give every interactive SVG element `tabindex="0"`, and draw focus with something other than `outline`. Two 2026 practitioner guides agree on the modern pattern for charts: a single tab stop with roving `tabindex` (exactly one descendant at `0`, the rest at `-1`, arrow keys move it and call `.focus()`), never intercepting Tab; `role="img"` on the root "collapses the element's subtree in the accessibility tree", so it must be removed (or replaced by `graphics-document` or a labelled group) the moment children become focusable; put `tabindex` on the point (`<circle tabindex="-1" role="graphics-symbol" aria-label="Pro plan, Week 2, 1,388 users">`), not on the decorative polyline (`aria-hidden="true"`); draw the focus indicator in-SVG (thicker stroke, larger radius) because "A browser's default focus outline ... is frequently clipped by the SVG viewport"; `focus({ preventScroll: true })` to avoid scroll jumps; `aria-activedescendant` is the lighter alternative but "has thinner SVG support"; and inside shadow DOM "focus and aria-activedescendant do not cross the shadow boundary the way you might expect; keep the roving marks and the container in the same tree, and expose a delegatesFocus host so Tab reaches the chart from the light DOM". The A11Y Collective adds the decorative case: give non-interactive inline SVG `tabindex="-1"` and `aria-hidden="true"` because "Browsers can be inconsistent about whether an inline svg becomes a tab stop". Sources: https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/tabindex , https://www.w3.org/TR/2026/WD-svg-aam-1.0-20260311/ , https://allyjs.io/tutorials/focusing-in-svg.html , https://www.accessible-data-interfaces.com/virtualization-charts-dynamic-data-displays/canvas-svg-chart-keyboard-interaction/ , https://www.interactive-data-visualization.com/accessible-interactive-data-visualization/keyboard-navigation-patterns/ , https://www.a11y-collective.com/blog/svg-accessibility/ (2026-09-03).

25. Text measurement without layout. In the browser, `SVGTextContentElement.getComputedTextLength()` returns the computed length of the rendered text as a float (MDN's example: 124.5 for "Hello, SVG World!" at 16px), which requires a live DOM and so is unavailable at build time. The declarative guard is `textLength` (on `<text>`, `<tspan>`, `<textPath>`) with `lengthAdjust` (`spacing` by default, or `spacingAndGlyphs`): "you can ensure that your SVG text displays at the same width regardless of conditions including web fonts failing to load (or not having loaded yet)". Server-side practice: Vega "uses Canvas (either in the browser, or via node-canvas) to calculate text metrics, regardless of the output renderer", and the 2020 issue shows node-canvas returning different widths for raster and SVG backing types (Cairo/Pango locks to the first canvas type created), with users falling back to overriding `scenegraph.textMetrics.width` or to "a lookup table for each character ... applied over the text and font size"; the js-server-text-width package is that lookup-table approach packaged (a browser tool emits per-glyph widths, two base64 characters per glyph); a Deno badge generator found a Skia canvas polyfill "off by a few pixels" and switched to glyph metrics from the font file; node-pretext wraps node-canvas `measureText`. boundsvg goes furthest: "Font shaping (rustybuzz, HarfBuzz-compatible) and layout (Taffy flexbox and CSS Grid) run in WASM against fonts you supply, so measurement is exact and the SVG ... output is identical regardless of environment"; it requires TTF/OTF/WOFF2 font bytes and does no OS font lookup "by design for deterministic output", and offers shrink-to-fit, wrapping and ellipsis. TanStack's position (finding 7) is the pragmatic middle: deterministic fallback metrics on the server, re-measure in the browser when fonts are ready. ## Recommendations for opt-chart

Prioritised. Each states what to do, why (with the finding numbers that support it), and the residual risk.

P1, decide now:

1. Data shape. Inline the chart's data as a `<script type="application/json">` child of `<opt-chart>`, emitted by Trunk at build time, and also accept the parsed object through a `data` property. The block holds tidy rows plus a small spec: `series` (id, label, unit, class index), `rows` (t, v1..vN), `marks` (t, label), `band` (from, to, label), `chapters` (from, label). Only primitives become attributes: `for`, `initial-width`, `x-unit`. `time` is a property with no attribute. Why: every surveyed element accepts rich data as a property and none reflects it (findings 1, 7, 9, 14); attribute JSON works (google-chart, vaadin-chart-series) but forces string parsing and quoting rules and grows with the dataset (findings 1, 2); a data block is spec-defined as content "the browser won't process", is CSP-safe, survives without JavaScript, and can later be referenced by id so two charts share one dataset (finding 15); `time` changes every frame, which web.dev's "currentTime" rule says must not reflect (finding 14). Declarative `<opt-series>` children (Vaadin, LWCC) are a reasonable v2 but add slotting and MutationObserver work we do not need for a static site. Risk: a data block cannot contain the sequence `</script`; escape it in the Rust serialiser.

2. Rendering and hydration. Trunk writes the classed SVG inside `<template shadowrootmode="open">` within `<opt-chart>`, so the chart exists before wasm loads and without it. The Rust element's constructor reads `internals.shadowRoot`; only if it is null does it `attachShadow` and render. Why: DSD is parser-attached, streamable and the spec-sanctioned way to ship shadow trees from a build (finding 20); the web.dev pattern is exactly this check, and skipping it empties the prerendered root (finding 20); TanStack's SSR contract (real size, deterministic output, stable keys) is the same discipline (finding 7). Keep every `<defs>` entry (band pattern, clip paths, markers) inside the chart's own shadow root; never reference a light-DOM `<symbol>` (finding 22); for the documentation pages that show an SVG in the light DOM, prefix def ids with the element id, as TanStack's `idPrefix` does (finding 23). Risk: DSD roots cannot be created through `innerHTML`, so any client-side re-parse path must use `setHTMLUnsafe` or rebuild through DOM APIs (finding 20).

3. Theming surface: classes, tokens, parts. The renderer emits only classes: `series-1..N`, `grid`, `axis`, `tick`, `tick-label`, `mark`, `mark-label`, `band`, `chapter`, `playhead`, `playhead-label`, `plot`, `background`. The shadow stylesheet maps them to tokens: `.series-1 { stroke: var(--op-series-1) }`, `.grid { stroke: var(--op-border) }`, `.tick-label { fill: var(--op-muted) }`. Add `--op-series-1..N` to `:root` in both themes and extend the Rust contrast test so each series token passes 3:1 against `--op-bg`, `--op-surface` and `--op-raised`, and series labels pass 4.5:1 where they are text. Export the same names as parts (`part="series-1"`, `part="playhead"`) so a page can write `opt-chart::part(series-2) { stroke-dasharray: 4 2 }` and `opt-chart::part(playhead):state(peeking)`. Why: Highcharts styled mode proves the class taxonomy and index-based series classes at scale, and Vaadin's `--vaadin-charts-color-N` proves the token tier; both keep geometry in code and appearance in CSS (findings 2, 3); `::part()` is Baseline since 2020 and composes with `:state()` (findings 19, 21); a theme change then re-styles with zero re-render, which is the whole point of the plan. Do not use `contrast-color()` for series or labels: it returns only black or white, browsers may use different algorithms, and MDN warns mid-tones fail (finding 21); our Rust test is the source of truth. `light-dark()` is optional because the tokens already flip per theme; if adopted, `color-scheme: light dark` must be set on `:root` (finding 21).

4. Events, properties and states. Emit `opt-chart-seek` (`detail: { time }`, a commit) and `opt-chart-peek` (`detail: { time }` or `{ time: null }` on leave), both `bubbles: true, composed: true`, only from user gestures on the chart, never in response to `time` being set by the film (finding 14). Subscribe to the film's `opt-film-time` broadcast by resolving `for=` in the chart's tree scope, and expose a `forElement` property beside the attribute, mirroring `commandForElement` and `interestForElement`, so cross-root wiring is possible without ids (finding 18). Mirror the film's custom states on the chart (`following`, `playing`, `pending`, `peeking`) through `ElementInternals.states`, so page CSS can address `opt-chart:state(pending)` and part-level `::part(playhead):state(peeking)` (finding 19). Why: prefixed composed CustomEvents are what google-chart and the wrappers do (findings 1, 9); the "host owns the value, component is presentation" split of the VLLNT scrubber and svelte-p5's media sync matches our film-owns-the-clock design (finding 12); attribute reflection of the clock through a parent, Nightingale-style, would force the chart to be nested inside the film (finding 17), which is not our layout. Uncertainty: the Context protocol is deliberately not for this (finding 16); a shared `<opt-clock>` ancestor is only worth it if a third follower appears.

5. Sizing. `:host { display: block; container-type: inline-size; aspect-ratio: var(--op-chart-ratio, 16 / 6) }` plus `:host([hidden]) { display: none }`; prerender at `initial-width` (default 640, like TanStack); in the browser, a ResizeObserver re-renders in wasm at the measured width so tick labels stay at CSS pixel size; put `vector-effect="non-scaling-stroke"` on every stroke so any transform (including a transient viewBox scale before the first re-render) keeps 1px rules; set the host `aspect-ratio` so the prerendered and re-rendered charts occupy the same box and nothing shifts. Why: re-render on resize is what every surveyed element that handles resizing does (findings 9, 13), and we already run Rust in wasm, so it costs nothing extra; the alternative, pure viewBox scaling, scales text with the container, which Build UI's recipe works around with three SVGs (finding 13); TanStack's `initialWidth` policy exists precisely to minimise "the first responsive adjustment" (finding 7); `non-scaling-stroke` is Baseline since 2020 (finding 13); `container-type: inline-size` also lets the stylesheet hide the chapter bar or thin the ticks below a width (finding 21).

P2, next:

6. Peek tooltip. Render the peek readout as `<output part="peek" popover="hint">` inside the shadow root and position it with `position-anchor` against an `anchor-name` on the playhead group, with a transform-based fallback while anchor positioning is only "newly available" (Baseline January 2026). Why: `popover="hint"` gives a tooltip layer that does not close menus, with light dismiss and Esc handled by the browser (finding 18); anchor positioning removes the JavaScript positioning code (finding 21). Do not depend on `interestfor` for hover: it is Chrome 142 only, its touch semantics are still being adjusted, and its event is non-composed (finding 18); the film's existing pointer logic drives peek.

7. Text metrics at build time. Measure tick and mark labels in the Rust build with rustybuzz plus ttf-parser against the same woff2 the site serves, as boundsvg does, so label placement (right-aligned y ticks, collision avoidance for mark labels) is exact and deterministic; where a label must fit a slot, also emit `textLength` as the guard against fonts failing to load. Why: finding 25 shows every server-side charting stack either ships font metrics or degrades to estimates; TanStack's "deterministic fallback, then re-measure" is acceptable for them because the browser re-lays out, but our prerendered SVG is the no-JS artefact and should be right on first paint. Risk: a font pipeline is build complexity; if it is too much, TanStack's approach (estimate at build, `getComputedTextLength()` re-measure in wasm after `document.fonts.ready`) is the fallback.

8. Focus. Keep the chart a single tab stop with the existing `role="slider"`, attach the shadow root with `delegatesFocus: true`, draw the focus ring in-SVG at 3:1 (a `.focus-ring` class mapped to `--op-accent`), never rely on the UA outline, and if marks or chapters ever become focusable use roving `tabindex` and `graphics-symbol` roles and drop `role="img"`. Why: finding 24, all of it; SVG-AAM's inclusion rules mean any element we give `tabindex` will appear to assistive technology, so unfocusable decoration must stay `aria-hidden`.

P3, later:

9. Publish a Custom Elements Manifest for `opt-film`, `opt-machine`, `opt-term` and `opt-chart` (attributes, properties, events, parts, custom states, CSS custom properties), generated from Rust doc comments, with a test that every listed attribute, event, part and state is exercised. Why: it is the shared machine-readable description that editors and doc tools consume (finding 26), and it doubles as the API contract for the other researchers' work.

10. Do not adopt now: scroll-driven animations (not Baseline, finding 21), container style queries (partial in Chrome and Safari, finding 21), the Context protocol (not for sibling wiring, finding 16), Reference Target (Chrome 152 only, spec still in review, finding 18). Consider View Transitions only for whole-chart data swaps, using `view-transition-group` scoping and gated on the reduced-motion token; same-document transitions are Baseline since October 2025 (finding 21).

## Open questions for the other researchers

- Accessibility: our chart is `role="slider"` on the SVG; `role="img"` would hide children (finding 24). If marks, chapters or the band become focusable, which pattern do we want: roving `tabindex` with `graphics-symbol` roles, or `aria-activedescendant` with stable ids, and what does the live region announce while following the film? Should `<label for>`, `aria-controls` and `aria-describedby` between `opt-film` and `opt-chart` across shadow roots wait for Reference Target (Chrome 152 today, Gecko pref off in Nightly, finding 18), or be set through `ElementInternals` ARIA reflection now (finding 19)?
- Timeline and scrubber UX: interest invokers define a platform notion of "interest" (hover with delay, focus, long-press, Esc cancels) and a partial-interest mode for keyboard users (finding 18). Should the chart's peek follow the same delays and Esc behaviour as the film's hover peek, and should a pending seek be a `popover="hint"` so it never fights other popovers? The framework scrubbers in finding 12 all separate "host owns the value" from "component draws"; does our press-drag pending seek on the chart need its own commit and cancel events, or does it reuse the film's?
- Rendering technology: finding 25 implies a build-time font pipeline (rustybuzz against the served woff2) for exact label placement. Is one prerendered width plus wasm re-render enough, or do we want two or three prerendered widths selected with container queries for the no-JS case? Does the renderer emit `textLength` on labels, and which classes or parts does the classed SVG need beyond the list in recommendation 3?
